rpc-svrkit架构

Svrkit介绍

微信后台的核心 C++ RPC 服务框架，WXG 技术架构部几乎所有后台服务都基于它开发。

它解决的是”业务只写业务逻辑”的问题。早期开发者要自己处理：协议解析、配置读取、日志、测试工具、服务发现、负载均衡、超时重试、限流熔断。Svrkit 把这些基础能力下移到框架，开发流程简化为三步：定义 proto → 生成框架代码 → 填充业务逻辑。

核心设计是网络层和业务层彻底分离：IO 线程用 epoll 收发包，Worker 是独立进程跑业务，中间用共享内存队列零拷贝传数据、socketpair 传就绪信号；业务逻辑跑在 libco 协程里，同步写法就能拿到高并发。

框架把服务治理全包了——路由发现、超时重试、过载保护、限流，业务只需要写 proto 接口和 serviceimpl，一个 proto 文件生成 client、server、测试工具全套。

要点：skgenerated/ 下是自动生成代码不要手改；唯一需要手写的源文件是 .proto，核心业务代码写在 <module>serviceimpl_pb.cpp。

调用过程

一次完整的 RPC 调用过程

Svrkit 的核心设计是网络层和业务层彻底分离，中间用共享内存队列传数据、socketpair 传信号。整条链路分四步。

第一步，建连接。 accept 线程进行监听，拿到FD，代表这条 TCP 连接的文件描述符，轮转分给某个 IO 线程。IO 线程为它创建一个会话对象，记录 FD、一个全局唯一的会话 ID和收包缓冲区，把这条连接注册到自己的 epoll 里。

accept 单独一个线程，是因为建连接很轻量，且不能让业务卡死影响新连接接入
epoll Linux 的 IO 多路复用机制：让一个线程同时盯住上万条连接，哪条来数据了内核就告诉你，不用一条条去问。三个调用：epoll_create 建实例 → epoll_ctl 把连接加进去（这就是”注册”）→ epoll_wait 等事件。关键优势：开销只和活跃连接数有关，与总连接数无关。10 万条连接里只有 50 条有数据，就只返回这 50 条。

第二步，收包并投递。 IO 线程 epoll 等到可读事件，把数据读出来追加到该连接的缓冲区，然后调 ValidatePkg 判断是半包还是整包——半包就留着继续等，收满一个完整包才处理。拿到完整请求后，把请求体加上会话 ID 等元数据打包，写进共享内存队列 InQueue，再往 socketpair 写一个字节通知 worker。

数据走共享内存是为了零拷贝，省掉管道那种用户态到内核态的两次拷贝；但共享内存本身不产生可读事件、挂不到 epoll 上，所以额外用 socketpair 传信号。数据要快，信号要能被 epoll 等到。

第三步，worker 执行业务。 worker 是独立进程，启动时已预创建一批协程。它一边等 socketpair 通知、一边轮询 InQueue，取到请求后使用空闲协程切进去执行。业务代码是同步写法，但执行到网络等待点会自动让出 CPU，调度器立刻切到别的协程处理下个请求，所以一个 worker 能同时在处理几十上百个请求。算完后把响应连同原样带回来的会话 ID 写进 OutQueue，再通知 IO 线程。

第四步，回包。  IO 线程被唤醒后从 OutQueue 取出响应。从响应中的会话 ID 去会话表里反查出会话对象，从中取到这条连接当前的文件描述符，再把数据写出去。如果查不到，说明这条连接在业务处理期间已经断开、会话对象已被销毁，那就直接丢弃这个响应。

为什么回包不直接用 FD而是会话ID？

worker 是独立进程，不持有 FD；回包时连接可能已断开并被新连接复用同一 FD，靠会话id才能确认会话没关。注意这里不能直接按 FD 发，必须用会话 ID 去会话表里查。因为 FD 会被复用——A 断开后它的 FD 7 被释放，B 连进来可能又拿到 7，只认 FD 就会把 A 的数据发给 B，造成串包。

共享内存 + socketpair 一起用

共享内存传数据，是为了零拷贝。 如果数据走管道或 socket，要经过用户态到内核态再到用户态的两次拷贝和两次系统调用；共享内存是两个进程直接读写同一块内存，零拷贝。IO 线程和 worker 之间过的是全量请求流量，这个差距是量级的。

共享内存有一个缺陷。 它就是一块内存，不产生任何可读事件，挂不到 epoll 上等待。如果只用共享内存，worker 只能忙轮询着扫内存，CPU 全耗在空转上。

所以补 socketpair 传信号——写完数据往里塞一个字节，socketpair 的可读事件能被 epoll 感知，worker 被唤醒后去共享内存取数据。一个字节把这个缺陷全补上了，代价约等于零。

数据要快，走共享内存；信号要能被 epoll 等到，走 socketpair。

追问：为什么不使用条件变量/信号/eventfd？

条件变量：跨进程要先建立在共享内存上（pthread 的进程共享属性），配置复杂，而且同样挂不上 epoll
信号（signal）：不能排队、会合并，两次写只触发一次处理——丢通知；信号处理函数里能干的事也严重受限
eventfd：确实可以（写 1 触发可读），和 socketpair 在这个角色上等价，svrkit 选 socketpair 是历史与全双工特性的考虑——说到这个层面就够了，再往下别编

Accept Queue/InQueue/OnQueue 满了

核心原则是“在还来得及的时候尽早拒绝，在来不及的时候认损失”

AcceptQueue 和 InQueue 满，走主动快速失败——连接刚建立或请求还没进业务，直接回失败甚至关连接，客户端拿到明确错误立刻换机重试。过载时可拒绝也不能排队，排队只会让延迟越滚越大、最后全部超时，那就是雪崩；快速失败才是把过载挡在业务之前。

InQueue 还有个细节：worker 取包时看排队时长，超过 500ms 就丢弃——因为客户端大概率已经超时不等了，处理了也白发

OutQueue 满就丢响应，只记日志，客户端超时。因为业务已经算完，没得回滚。但这个极少发生——IO 线程发包是微秒级、worker 算业务是毫秒级，瓶颈永远在 worker，InQueue 必然先满，轮不到 OutQueue。

追问：“假失败响应”是什么？

MakeFakeResp：不经过业务逻辑，框架直接构造一个失败包回去——客户端拿到明确的失败码，而不是干等超时

进程间通信为什么选共享内存？

svrkit 里 IO 线程（网络进程）和 worker（独立进程）之间传请求，选的是共享内存环形队列 + socketpair 通知的组合。拆开说为什么是这两个：

数据走共享内存，为了零拷贝。如果用管道或 socket，数据要走”用户态 → 内核态 → 用户态”，两次拷贝加两次系统调用；共享内存是两个进程直接读写同一块物理内存，零拷贝——对每个请求都要过的主干道，这个差距是量级的。

信号走 socketpair，因为共享内存”不会响”。共享内存本身不产生可读事件，挂不到 epoll 上等待；而 IO 线程的事件循环需要统一的触发源。socketpair 每次只写一个字节，代价极小，却让”worker 干完活了”这件事变成 epoll 可等的事件。

数据要快，信号要能被 epoll 等到——各取所长。
顺带一个运维细节：checkmaster 机制——网络进程每 10 秒检查 worker 组 master，发现任何一个丢了就 kill(0, SIGKILL) 自杀整个进程组，交给外部守护重启。宁可整机快速重启、名字服务切走流量，也不留一个半死不活的进程处理必失败的请求。

零拷贝技术

内核提供的主要是三个：sendfile、splice、mmap。

sendfile：文件到 socket 的专用通道，数据从页缓存直接进 socket 缓冲，全程不出内核；网卡支持 SG-DMA 的话连这一次 CPU 拷贝都省掉，只传“地址+长度”的描述符。nginx 发静态文件、Kafka 把日志段发给消费者就是它。局限是只能文件到 socket，方向单向，而且数据不经过用户态——用户代码根本摸不到数据。

splice：比 sendfile 灵活一点，通过管道把任意两个 fd 在内核里衔接起来，数据在内核缓冲间移动。但同样是“内核内摆渡”，数据不落地用户态。

mmap：把文件映射进用户地址空间，省掉“页缓存 → 用户缓冲”的一次拷贝。数据倒是进用户态了，但每次传输还是要走系统调用进内核。

然后是共享内存：两个进程把同一块物理内存映射进各自地址空间，之后读写就是普通内存访问——零拷贝、零系统调用。

svrkit零拷贝使用共享内存

① 两端都是用户态进程，且都要处理数据本体。 IO 线程要组装请求包，worker 要解析并执行业务——数据两端都要被代码摸到。而 sendfile/splice 是“内核内摆渡”，数据不进用户态，第一个特征就不满足，直接排除。

② 双向高频。 请求走 InQueue、响应走 OutQueue，一来一回都是全量流量。共享内存映射一次、终身使用，每次传输连系统调用都不用；mmap 方案每次还得进内核。

③ 要在内存上构建数据结构。 传的不是裸字节流，是“请求体+元数据”的结构化消息——共享内存上可以直接建环形队列、管理读写指针、控制边界；其他方案都没有“在通道上自由建结构”的能力。

一句话：sendfile/splice 解决的是“转发”的零拷贝——数据借道内核就走；svrkit 要的是“协作”的零拷贝——两个进程共同操作一块数据，那只能是共享内存。

共享内存的代价：没有同步原语——所以 svrkit 要自己配 socketpair 传信号、用环形队列+原子指针做无锁队列；生命周期管理——进程崩了内存还在（内核不回收，要显式删除或靠引用计数）；安全性——任何持有映射的进程都能写，一块写坏全完，所以只适合自己信任的进程组之间用。

序列化协议

svrkit 用 Protobuf 做序列化，上面再包一层自研的 TLV Pickle 协议封装。

分两层说。

内层 Protobuf 负责”数据怎么表示”：二进制编码，体积比 JSON 小很多，编解码不需要解析文本所以快得多；而且 proto 文件本身就是接口契约，强类型。

外层 TLV Pickle 负责”请求怎么路由”：它在 Protobuf 之上加了 Magic（模块号）和 CmdID（接口号）。Magic 建模块时在 poseidon 申请、全服务共用；CmdID 每个 rpc 方法一个、从 1 递增——两者拼起来构成”服务名 + cmdid”的全局唯一标识，服务端 dispatcher 靠它把请求路由到正确的处理函数。

不用 JSON 的三个理由：一是体积和编解码速度；二是强类型契约，编译期就能发现字段错误；三是向后兼容——protobuf 的字段编号机制允许只加可选字段不改老字段，服务端升级后老客户端照常工作。

由此也带来 svrkit 的硬约束，这些是”协议即契约”的直接体现：cmdid 上线后不能改；字段编号、字段类型、服务名、方法名都禁止改；只能加新的可选字段或标 deprecated，不能删字段。

网络模型

网络模型怎么样

svrkit 是主从 Reactor 多线程模型，主 Reactor 是 accept 线程，只负责建连接、拿 FD，然后轮转分给从 Reactor；从 Reactor 是 N 个 IO 线程，每个线程一个独立的 epoll，负责已建连接的读写。

在标准模型上 svrkit 做了两个改造： 

  • 一是计算做了进程级分离——业务 handler 不在同进程的线程池里跑，而是独立的 Worker 进程，靠共享内存队列传数据、socketpair 传信号。业务代码 coredump 只挂自己的 worker，master 秒级拉起，网络层完全不受影响。 
  • 二是 handler 协程化——Worker 里跑的是 libco 协程池，hook 系统调用，业务同步写法拿到异步性能。
  • 工程上：连接和 IO 线程绑定——一条连接从头到尾只归一个线程管，收包缓冲区、半包状态都只被它访问，天然无锁；也不会有多个线程抢同一事件的惊群。

追问：epoll了解吗？

epoll 是 Linux 的 IO 多路复用机制，解决的问题是：一个线程同时监听海量连接，哪条就绪了内核只通知哪条。

三个系统调用：epoll_create 建实例（它自己也是个 fd）；epoll_ctl 把要监听的连接增删改进去，只注册一次；epoll_wait 阻塞等待，返回的就绪列表。

它比 select/poll 快在两点：一是 fd 全部维护在内核的红黑树里——select/poll 每次调用都要把整个 fd 集合从用户态拷进内核、返回后还要 O(n) 遍历找哪个就绪，epoll 的 ctl 只注册一次；二是事件到达靠回调——数据到了，内核通过回调把对应项挂进就绪链表，epoll_wait 只拷贝这个链表出来，开销从 O(总连接数) 降到 O(就绪数)。10 万条连接只有 50 条有数据，就只处理这 50 条。

还有两种触发模式：LT 水平触发——只要缓冲区还有数据没读完就一直通知，编程简单不怕漏读；ET 边缘触发——状态变化只通知一次，必须循环读到 EAGAIN，省通知开销但容易踩漏读的坑，而且 ET 必须配非阻塞 fd。svrkit默认是 LT。

追问：为什么每个线程一个独立 epoll？共享一个不行吗？

共享一个 epoll 有两个问题：一是惊群——一个事件来了把多个阻塞在 epoll_wait 的线程全唤醒，只有一个能干活，其余白醒；二是连接的收包缓冲区会被多个线程碰，得加锁——而缓冲区是每个包都要碰的热点数据，锁代价太高。独立 epoll + 连接绑定线程，两个问题一起消掉。

追问：惊群具体是什么？

多个线程/进程在等同一个 fd 上的事件，事件到达时内核把所有等待者都唤醒，但只有第一个能 accept/读数据，其他全白跑一趟——唤醒的开销全是浪费。经典场景是多进程 listen 同一个端口。

“epoll 和 select/poll 的区别？”（操作系统通用题，备着）

select 三点不足：fd 数量硬上限（1024）、每次调用要全量传 fd 集合、返回后要遍历找就绪的；poll 去掉数量限制但遍历还在。epoll 把 fd 维护在内核的红黑树里（epoll_ctl 增删），事件到达时回调挂进就绪链表，epoll_wait 只返回就绪的那批——开销从 O(总fd数) 降到 O(就绪数)。这正是它能扛海量连接的根本。

模型：

怎么抗住高并发

Svrkit 抗高并发是四层手段叠出来的。

第一层，IO 线程用 epoll。 epoll 的开销只和活跃连接数相关，与总连接数无关：10 万条连接里只有 50 条有数据，就只返回这 50 条。每个 IO 线程一个独立 epoll、连接与线程绑定——缓冲区只被一个线程碰，天然无锁；也不会有多线程抢同一事件的惊群。

第二层，业务用协程。 Worker 里 RoutineCnt 个协程共享线程，业务写的是同步调用，但 libco hook 了系统调用：走到网络等待点协程自动让出，切去处理别的请求，回包再切回。本质是把等待时间重叠了——请求的大头耗时是等网络而不是算 CPU，等的时候 CPU 让给别人。这就是“同步写法、异步性能”，一个 worker 同时挂上百个在途请求。

第三层，总并发 = IOThreadNum × worker进程 × RoutineCnt，三个参数相乘（比如 3×30×100=9000），容量不够加配置、加机器。Worker 是独立进程，一个崩了 master 秒级拉起——只损失它手上的几个请求，高并发之下依然不雪崩。

第四层，过载保护。 AcceptQueue 满关连接、InQueue 满回假失败包、排队超 500ms 直接丢弃。原则是宁可拒绝也不排队——排队会让延迟滚雪球、最后全部超时；快速失败让客户端立刻换机，保住已经接入的流量。

追问：三个参数分别怎么调？

IoThreadNum 建议核数的四分之一、最少 3——IO 线程很轻，不用多；StartProcs 在 svrkit 模式下是每个 IO 线程的 worker 数（注意和 summer 不同，summer 里是全局总数，同配置下 svrkit 的 worker 是 summer 的 IOThreadNum 倍——迁移最容易踩的坑）；RoutineCnt 加大要算内存——每协程默认 128K 栈，一个 worker 开 100 个协程就是约 13M，乘以 worker 数、进程数，栈内存是乘法关系。

追问：Worker 崩了影响多大？

只丢它手上正在处理的几个请求——别的 worker 不受影响，网络层更不受影响。worker-group master 自动拉起新进程补位，coredump 自动上报。这就是当初做“计算进程级分离”的收益：崩溃半径被切到单个进程。

追问：为什么用协程不用线程？

三个数：切换开销——协程是用户态纯汇编切寄存器，纳秒级，线程要陷入内核，微秒级；内存——协程栈 128K，线程栈默认 8M，一个数量级的差距；调度——协程是协作式，只在明确的等待点让出，没有抢占的锁竞争问题。所以在“一个请求一个并发单元”的 IO 密集场景里，协程能开到线程的百倍数量。

同步调用还是异步调用？

表面上是同步的——int ret = client() 一行调用、一行拿结果，业务写起来就像本地函数。底层靠协程做到异步性能：这行调用执行时，当前协程在网络等待点自动 yield，worker 里的其他协程继续跑；回包后协程被唤醒接着执行。

① 并发的本质是 IO 等待重叠，不是多核并行。一次请求里并发调多个下游（用 BatchTaskRun 或 Xwi 的任务池），是多个子调用的等待时间重叠了，CPU 上同一时刻还是跑一个协程。想要多核得靠多进程/多线程。

② svrkit 没有真正的 fire-and-forget。起了协程任务但不读返回值，照样阻塞到全部完成——等待发生在调用语句本身，跟后面用不用返回值无关。历史上的 wqueue 异步方案想做这个效果，已废弃不能用。能控制的只是”结果回来后要不要处理错误码”。

单请求内并发多子调用用 BatchTaskRun：每个子任务一个协程，IO 等待重叠。它用的是独立的私有协程池（RoutineCnt × MaxBatchCnt），和接请求的 worker 协程池物理隔离——所以加再多任务也挤占不了正常请求的协程；真正的风险是把并发度参数 num 调太大，挤占的是同模块其他也在用 BatchTask 的业务。

服务发现

同IDC、跨IDC路由发现/服务发现

svrkit 的服务发现不是每次调用去查注册中心，而是读本地的路由配置文件。注册中心只负责把文件同步到每台机器上。

1、文件怎么来的：

微信自研了一套名字服务叫 RouteSvr，svrkit 里内置了一个上报进程，把本机的服务信息报给 RouteSvr，RouteSvr 写进 ZooKeeper；然后每台机器上都装了一个 ZkAgent，定时从本 IDC 的 ZkAgentProxy 主动拉取，把路由落成本地文件。

 pull 不是 push，而且 agent 只找本 IDC 的 proxy 拉——跨城的压力就被隔开

2、客户端怎么找到对应文件

核心的机制是IDC路径扩展，生成的生成的 client 代码里写的是不带 IDC 的标准路径（/etc/client/mmxxx_cli.conf），调用时框架拿它按顺序探四层，哪层先命中就用哪层。

  • 查 global/meta.conf。 负责只在一个 IDC 部署的模块，这种模块的路由文件直接放在 global 目录下，光看路径不知道它属于哪个 IDC，要靠 meta.conf 查看该模块的归属。这套已废弃。
  • 查 global/halfmeta.conf。 负责只在某几个 IDC 部署的情况，按主调 IDC 分段：[camel] xxx=shanghai、[hk] xxx=shenzhen——西北的主调去读上海目录，香港的主调去读深圳目录
  • 看本机 IDC 目录。 本机是哪个 IDC 从 sysmeta.conf 读。对应最常见的“每个 IDC 都部署了，各访问各的”
  • 兜底看标准路径本身。 还没有就直接返回加载失败。
  • 注：前三层都是探测etc/route/ 体系下的位置，而第四层是回到 etc/client/ 下的原始路径看文件本身在不在

同IDC路由和跨IDC路由

框架都从最终读取的文件路径里取出目标模块的 IDC，和本机 IDC 一比：

  • 一致 → 同 IDC：一般是第三层命中，读本机目录，直连 + 模块默认超时
  • 不一致 → 跨 IDC：一般是第二层被 halfmeta 指走，读别人的目录，走 IdcAgent 代理 + 换跨 IDC 超时（代理做了链路优化和长连接复用，比裸连跨城更快更稳）

同IDC还有就近园区的优化

同 IDC 内不同园区也有耗时差异（同园区省约 10ms）。开启 UseNearByZone=1 后，不同园区的 client 看到的机器权重表不一样：同园区先消化，吃不下的按比例溢出。不过这个是只有第一次 RPC 走就近，重试退回一致性哈希均匀打散——重试说明近处已出问题，不该再往近处挤。

一个 IDC 内部有多个物理园区（zone），走同园区省时点。机制就是不同园区的 client，看到的权重表不一样传统路由下所有 client 看到的机器权重是一样的，流量均匀打散；就近园区则让每个园区的 client 算出一张只属于自己的权重表，逻辑是“同园区先消化，吃不下的按比例溢出”。

追问：为什么使用IDCAgent代理？

跨城链路的物理现实是：RTT 大、丢包率高、连接建立慢。如果每个业务进程都自己直连远端 IDC 的机器，会发生：

  1. 跨城连接数爆炸——每个进程对每台远端机器都要建连接，几百个进程 × 几十台机器，城间链路被海量连接占满
  2. 每次建连都慢——TCP 三次握手要吃一个完整的跨城 RTT，断了重连又是
  3. 难做链路优化——散落的直连，没法统一调度线路

所以使用了IdcAgent代理，它是一个一台部署在每台服务器上的跨城代理进程。

业务进程调跨 IDC 的模块时，不自己发跨城连接，而是把请求交给本机的 IdcAgent（本机通信，几乎零开销）；由 IdcAgent 负责和远端 IDC 建立并维护连接，把请求转过去、响应转回来。
收益：跨城连接被集中起来长连接复用（N 个业务进程的请求可以共享少量几条跨城连接），建连成本摊薄；而且可以对跨城链路做统一的线路优化和选路。所以实测走代理比裸连跨城更快也更稳。

为什么使用文件式的服务发现

优点

1、规避海量客户端直连 ZK 带来的压力。 如果成千上万个业务进程，每个都创建 ZK 客户端、注册 watcher，ZK 集群连接数会爆炸；服务上下线，watcher 事件广播风暴，ZKCPU、网络扛不住。 现在只有每台机器上 1 个 Agent 连 ZK，一台机器不管跑几十个上百个业务，就一份 ZK 连接，极大降低注册中心压力。

2、业务进程完全不依赖 ZK 可用性。 哪怕 ZK 集群挂掉、网络分区：Agent 不会立刻坏掉，本地磁盘已经有路由快照文件。业务 RPC 直接读本地文件，RPC 调用完全不受注册中心故障影响。 传统模式：业务进程自己做 ZK 客户端，ZK 断连，watcher 失效，部分场景会拿不到服务列表，业务风险高。

3、降低故障的影响面，所有数据都是落在本地的，他可能有些数据坏了的话，他不会影影响面不会那么大。就如果你是全部访问远程的话，远程服务里面如果那个数据可能有问题的话，就所有人都拉到一个错的数据

4、性能收益：RPC 路径上没有任何远程网络 IO。 每次 RPC 做服务发现，就是读本地磁盘文件（内存缓存，实际很少真正磁盘 IO），没有网络往返，延迟极低。

缺点

1）数据不是实时，是最终一致性。 Agent 定时拉取，路由变更，要经过 MQ → ZK 代理 → Agent 拉取 → 落盘文件 → 业务框架加载文件，存在延迟窗口。服务刚上线，别的机器不能立刻看见实例，要等同步。 传统 ZK‑watcher 是推送，变更毫秒级感知；这套是准实时。适合内部业务，不能容忍延迟的场景就不适合。

2）存在本地文件脏数据风险。 Agent 进程 crash，机器重启，要保证路由文件可以正常更新；如果 Agent 挂了不再更新，本地文件是旧的，会访问已经下线的实例。 所以业务层 RPC 必须要有连接健康检查、故障剔除，不能完全信任本地路由文件。

3）版本、哈希校验。 Agent 落盘文件带上版本号 + md5；业务 RPC 框架加载文件，对比哈希，只有文件内容真正发生变化才重新加载路由，避免频繁刷新负载均衡组件。

4）区分：和普通本地缓存不一样 Dubbo/brpc 也会把注册中心结果缓存本地文件，但客户端本身依然要维持 ZK 长连接订阅。 微信这套是：业务进程完全没有 ZK 客户端，全部交给机器级 Agent 代理，业务只读磁盘文件。

上海的机器A挂了要使用使用深圳的机器B，svrkit怎么路由

这里要分两个层次看——单机故障和 IDC 级故障，svrkit 的处理完全不同。单机挂了是在本 IDC 内解决的，不会跨城；跨 IDC 在微信后台是静态的部署选择，不是故障自动切换。

第一层，单机故障（A 挂了）：

走的是同 IDC 内的换机重试加屏蔽。客户端调用遇到系统失败——连接失败、收发包失败、被快速拒绝这几类——框架会自动换一台机重试，默认 3 次；连接阶段还有独立的重试次数。候选机器来自客户端配置里的 Server 列表，全都是本 IDC 的机器。

光重试还不够，否则每次都要先踩一遍死机。所以还有屏蔽机制：失败次数在一个周期内累计到阈值，这台机就被屏蔽掉，后续请求不再选它，过一段时间再试探性放量。屏蔽有两级，一级是线程内计数，一级是跨进程的漏桶熔断，后者默认开启。

所以真实表现是：前几个请求打到 A 失败但重试成功，用户无感；很快 A 被摘掉，流量全部走本 IDC 其他机器。全程不会去深圳。

**第二层，IDC 级故障：

至于整个 IDC 挂掉，那已经超出 svrkit 客户端的能力范围了，属于运维侧的路由变更和接入层流量调度。我知道的是路由变更工具支持按园区、IDC 粒度灰度摘流量，跨 IDC 的指向配在 halfmeta 里可以改；另外 idcagent 有个 UseRawTcp 开关，出灾时可以让全网绕开代理直连。再往下的完整出灾预案我没有实际参与过

那什么时候才会用深圳的机器？
只有当这个模块本来就规划成”深圳部署、上海跨过去访问”的时候。而且出发点不是容灾，是成本——某些模块调用量集中在一个 IDC，其他 IDC 调用很少，每个 IDC 都部署一套不划算，就让调用少的 IDC 跨过去访问。这是规划好的常态路由。

实现上，微信的路由是按 IDC 分目录的文件，比如 route/shanghai/xxx_route.conf、route/shenzhen/xxx_route.conf。框架完成一次调用要知道两件事：本机在哪个 IDC，从 sysmeta.conf 里读；目标模块在哪个 IDC，解析路由文件路径得到。一旦发现两者不一致，默认走 IdcAgent 代理过去，因为代理比裸连跨 IDC 更快更稳定。

具体哪个 IDC 跨到哪个 IDC，配在 halfmeta.conf 里，比如配西北的主调去访问上海部署的模块。关键是：没配跨 IDC 的 IDC，访问这个模块就是直接失败，不会自动兜底到别的 IDC。

“为什么不做成自动跨城容灾”，可以答：跨城延迟比同城高一个量级，自动切过去可能把一个局部故障变成全局雪崩（本来只是几台机的问题，结果整个 IDC 的流量涌向另一个 IDC 把它压垮）；而且跨城要考虑数据一致性和带宽成本。所以微信的选择是同城内自愈，跨城靠人工/预案决策。

连接生命周期管理

长连接还是短连接？

长连接为主，空闲 30 秒回收。

为什么长连接：建连是有真实成本的——TCP 三次握手吃一个 RTT，新连接还有慢启动；RPC 是高频调用，每次调用都建连的话，这些开销乘上 QPS 就是灾难。长连接建一次、复用千万次。

但长连接不能只建不收——连接是资源：一条占一个 FD、一份会话对象、一点缓冲内存。所以配空闲超时 30 秒：有流量的连接一直活着，30 秒没流量的回收。这解决了“僵尸连接慢慢耗光连接数”的问题。

连接数还有总量闸门：MaxConnections 默认 102400，超了直接 close 返回 -208——这同时是过载保护的第一道门，把过量的连接挡在最外面。再配建连限速（每毫秒最多发起数），防连接风暴。

客户端这一侧同样长连接复用，由 connagent/idcagent 连接代理管理；跨 IDC 走 IdcAgent，它把跨城长连接集中池化——几百个业务进程共享少量几条跨城连接。建连参数单独配：connect 重试 5 次、建连超时 200ms——比读写超时短得多，因为建连失败换机很便宜，不值得等。

连接怎么管理？

管理的核心是：每条连接是一个有状态的会话对象，而且只绑定一个 IO 线程。

1、绑定。 accept 线程拿到 FD 后轮转分给某个 IO 线程，IO 线程创建会话对象——FD、全局唯一的会话 ID、收包缓冲区、状态——注册进自己的 epoll。从此这条连接的读写只归这个线程，缓冲区天然无锁。

2、使用。 两个方向的细节：收方向，TCP 是字节流没有消息边界，IO 线程把数据追加进该连接的缓冲区、攒满一个完整包才投给业务——半包状态记在会话对象里，跨多次读事件存在。发方向，响应写进内核发送缓冲区；写不完不丢弃（响应是算完的结果），挂可写事件等下次接着发。

3、解绑。 客户端断、服务端关、或空闲超时——断开时把会话对象从会话表里删除。为什么删除这么关键：内核分配 FD 用最小可用整数原则，这条连接的 FD 释放后，下一条新连接很可能拿到同一个 FD。所以全程认会话 ID 不认 FD——worker 回包带着会话 ID 来查表，查不到就是连接已断，响应丢弃，绝不误发。

注：连接断开不撤销在途请求。请求只要进了 InQueue，worker 照样算完——只是响应按会话 ID 查不到、无处投递而已。处理和连接是解耦的，客户端靠超时加换机重试兜底。

负载均衡

svrkit负载均衡

svrkit 的答案比较特别：负载均衡策略是多元化的，按业务的数据特性选。

机制上，_cli.conf 的 Server 列表每台机器带 Scale 权重，支持加权轮询这类基础能力；在此之上有一致性哈希（ConsistenHash / UseHrwHash）和按号段路由等——有状态、数据分片的业务用一致性哈希让同一个 uin 稳定落到同一台机器，无状态的用轮询打散。

进阶的还有就近园区路由：同一个 IDC 内不同物理园区也有耗时差异（实测同园区省 10ms 左右），它的思路是不同园区的 client 看到的权重表不一样——同园区先消化，吃不下的按比例溢出。比如我园区主调只有 10% 流量、同园区下游有 14% 机器，那在我眼里其他园区机器权重直接是 0。而且只有第一次 RPC 走就近，重试退回一致性哈希均匀打散——重试说明近处出问题了，不该再往近处挤。

一致性哈希算法对比优劣

一致性哈希要同时满足四个性质：平衡性（key 均匀分布）、单调性（加节点后 key 要么留原地要么去新节点，不能乱迁）、稳定性（扩缩容时迁移量尽量少）、性能（计算快）。所有算法都是在这四者间取舍。

1、哈希环

把节点按权重 hash 成大量虚拟节点，撒到 2^32 的环上；key 也 hash 到环上，顺时针找最近的一个虚拟节点，虚拟节点反查真实节点。

优点：单调性好；虚拟节点够多时平衡和稳定都不错；实现简单、可观察性强——应用最广（memcache、redis 客户端、dubbo、nginx、envoy）。

缺点：内存大——虚拟节点数 = 权重 × 节点数，全存着；虚拟节点少时平衡性差——100 个节点标准差 10%，1000 个才降到 3.2%。查找 O(log vn)。

2、跳变哈希

原理很数学：节点数从 n 变 n+1 时，恰好 n/(n+1) 的 key 不动、1/(n+1) 跳到新节点——用随机数模拟跳变，返回最后一次跳变的位置。只要求“节点按 0..n-1 编号”。

优点：平衡性碾压一切——标准差 0.000000764%；零虚拟节点、内存几乎为零；计算 O(ln n) 比哈希环还快。guava 标准库、微信后台的 cachesvr 都在用。

缺点：缩容单调性差——缩容时 1/n 的 key 会乱跳（扩容才单调）；不好支持权重（依赖有序编号）；节点挂了不能自动摘除，要自己做容错（副本或 doubleHash）。

3、maglev，查找最快

两张表：每个节点一张排列表（它想占哪些槽），再按固定规则填一张查找表（比如 65536 个槽，每个槽指向一个节点）。查的时候 hash 取模槽位，O(1)。

优点：查找 O(1) 最快；内存固定（就一张 65536 的表）；平衡性比 ketama 好（方差 6~7%）。

缺点：建表有开销——平均 O(MlogM)，最坏 O(M²)；稳定性是短板——缩容后迁移的 key 是 ketama 的两倍。envoy 和 Google 内部网关在用；微信北极星的就近路由实现就是 maglev（排列表 65537，hash 用 Murmur3_64）。

4、HRW，最高随机权重

最朴素的思路：对每个 key 独立算 h(key, node_j)，谁大选谁。

优点：不需要环和虚拟节点，存储省；平衡性、单调性和 ketama 相当。

缺点：每次 O(n)——key 要和所有节点都算一遍，节点多了就慢；业界用得少。

超时、熔断、降级、限流

超时怎么设？

由主调方在自己的 route.conf 里配，不是被调方声明——被调方不知道主调的 SLA。三个参数：建连超时 200ms、建连重试 5 次、读写超时按接口配。

值怎么定：没有公式，靠压测和线上观测耗时分布（重点看 P99），经验设为平均耗时的数倍。两条红线：① 下游接口超时必须小于上游给自己的超时，否则“下游还在算、上游已判失败重试”，连锁放大；② 超时低于该接口 P99 的 1.2 倍即判异常——频繁误杀长尾请求。

另外跨 IDC 有专门的超时配置——判定跨城后自动切换，因为 RTT 完全不同量级。

EMA 动态超时

静态超时两难：设大了，下游故障时上游陪等；设小了，误杀长尾。EMA 用滑动平均盯下游耗时，动态收缩：正常态用上限值保长尾成功率；下游平均耗时升高（异常态）自动收紧到下限，及时止损。平滑系数控制灵敏度。

但收紧会放大重试量——超时变短→更多失败→自动重试→流量放大，所以官方要求 EMA 配合重试 quota 一起开。这就引出核心认知：超时从来不是独立参数，它在一条因果链上。

EMA 动态超时：配置一个上限和下限，正常时用大超时保长尾成功率；下游平均耗时升高（异常态）时自动收紧到下限，避免拖垮上游。但注意收紧会让重试量上升，要同时开重试 quota。

EMA 具体怎么算？ → 平滑系数 SockTimeoutEmaN，越小越灵敏

失败了怎么办？重试和幂等怎么做？

先分类再谈策略。失败分两类：系统失败和业务失败。

系统失败——连接失败 -201、收包失败 -202、发包失败 -203、被快速拒绝 -206、超连接上限 -208——这类失败的特征是”换台机器大概率就好了“，所以由框架自动换机重试，默认 3 次（MMClientCallRetryCount）；connect 阶段还有独立的 5 次重试。业务代码拿到非 0 直接向上返回，不用自己写重试。

业务失败——业务逻辑自己返回的错误，比如余额不足——绝对不重试。重试业务失败等于重复执行，余额扣两次就是事故。这个区分是重试设计的核心。RPC 是尽力而为，不保证不丢。队列满、进程崩、重启都可能丢在途请求；校验和只防数据损坏、不防丢。所以丢了靠调用方超时重试 + 业务幂等兜底；真要”绝对不丢”（比如支付异步通知），应该用 wqueue 这种可靠消息队列，不要拿 RPC 当 MQ 使。

幂等的实现是业务的责任：常见做法是带唯一 ID，处理前查重。

  • 重试会不会打爆下游？ → 3 次上限 + 换机（不重复打同一台）+ FastReject 时 client 缓存拒绝信息少发请求
  • 屏蔽机制呢？ → 重试只是止血，还有屏蔽防止反复踩死机：线程级 FailCount=4，跨进程漏桶 NewFailCount=50，满了摘机、过周期再试探（

熔断、限流、降级分别怎么做？

屏蔽，对应熔断：分两级。
线程级——一个周期（60 秒）内失败满 4 次（FailCount），本线程屏蔽这台机器；
跨进程级——单线程视角样本太少、误熔断概率高，所以有跨进程漏桶（NewFailCount=50，UseMMTrafficMgr 默认开启）——把整个进程所有线程的失败汇进一个漏桶，攒满 50 次（NewFailCount）就屏蔽

屏蔽是带恢复的：过周期再试探性放量，机器活了就回来。

追问：为什么用漏桶不用固定阈值？

固定阈值的问题：流量高峰期正常的失败基数也大，容易误熔断健康的机器，把容量雪上加霜。漏桶按速率平滑统计——单位时间漏掉多少、留下多少是恒定的，短时突发失败灌不满桶，只有持续性失败（真挂了）才触发。本质是把“失败了多少次”换成“失败的速率异常了没有”。

限流，是主动控制：不在 svrkit 框架内建，走北极星限流平台，可精确到 cmdid 维度。阈值要压测定：取压测极限的七八折留安全余量。

过载保护 降级：① FastReject：入队前检查，队列平均等待超 20ms 或 CPU 超 90% 直接拒绝，返回 -206——不做无意义的排队； ② 假失败响应：InQueue 满时框架直接构造一个失败包回去，客户端拿到明确错误而不是干等超时； ③ 排队超时丢弃：排队超 500ms 的请求直接丢——客户端早就超时了，算完也白发。

核心就是：宁可拒绝也不排队——过载时排队会让延迟滚雪球、最后全部超时，快速失败才保得住已接入的流量。

联动：缩短超时 → 更多请求被判失败 → 系统失败自动换机重试 3 次 → 流量放大最高 3 倍 → 更多机器被压到 FastReject 阈值 → 拒绝的请求又触发重试 → 失败计数快速累积 → 误熔断健康机器 → 剩余机器承接全部流量 → 更快过载——恶性循环。

所以三个实践约束：EMA 动态超时要配重试 quota；重试次数要和下游容量挂钩；屏蔽阈值（漏桶）要扛得住重试放大的失败基数。
