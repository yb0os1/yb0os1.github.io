wqueue

WQueue 面试题 · 面试口述专用

配套主题库《WXG面试-中间件题库（svrkit-ttlkv-tablekv-mq-wqueue）.md》WQueue 章（Q74~Q79）使用。
本册视角：面试官按”Kafka / 消息队列”通用知识提问时，把标准答案落到 WQ 的具体实现上。

开场定位：WQ 是什么？（必背）

WQ 是 WXG 基于 WFS 分布式文件系统构建的分布式消息队列，官方文档明确说”概念与 Kafka 类似，可以对照理解”。

最精确的一句话概括：WQ = Kafka 概念层 1:1 复刻 + 存储/协调层腾讯化——把 Kafka 自管的两大件”外包”出去了：存储外包给 WFS（3 副本容灾由 WFS 保证，broker 无状态），协调外包给 Chubby（元数据和分布式锁，替代 ZooKeeper/KRaft）。

介绍 WQ 的最佳顺序：先说 Kafka 的概念都通用（Topic/Partition/ConsumerGroup/Rebalance/offset），再讲两处外包带来的连锁差异——这是它和 Kafka 拉开差距的全部来源。

概念映射表（先背熟，是所有题的地基）

Kafka WQ 说明
Broker queuesvr（入队）+ broker（出队） 两者都无状态，数据托管 WFS
Controller + GroupCoordinator WqScheduler 分区调度 + 消费组协调
ZooKeeper / KRaft Chubby 元数据 + 分布式锁
Topic / Partition 完全相同 —
ConsumerGroup + member 完全相同 心跳、路由
分区分配（Range/Sticky） 一致性哈希 缩容迁移最小
__consumer_offsets topic Chubby 目录 offset/ 按数据所在 IDC 分开记
副本 + ISR WFS 3 副本 存储组件托管，无 ISR 概念
事务消息 PublishTxMsg + 反查 两阶段 + 反查兜底
幂等生产者 入队去重（unique_id） —
延迟消息 PublishDelayMsgAt/After ≤30 天
—（Kafka 无） 推模式（默认） consumeragent 回调业务 RPC

Q1 消息队列是干什么的？你为什么需要 WQ？

面试官想考什么：先考通识——MQ 的三大价值，看你是不是”为了用而用”。

口述答案：

消息队列的价值三个：解耦（上游不用知道谁消费）、削峰（流量洪峰先进队列，消费者按自己的节奏处理）、异步（不需要同步等结果的活儿扔进队列）。

但要用 WQ 这种分布式 MQ 而不是本地队列，是因为它再补两个能力：不丢（多副本持久化，机器坏了消息还在）和水平扩展（消费者加机器就能提吞吐）。

举个微信后台的典型链路：处罚系统判罚后要发通知、写流水、更新画像——这些下游不需要同步等结果，一条消息进 WQ，各消费者各自订阅；判罚主流程的耗时不受下游影响。

选型上的分界线：模块内异步、要求毫秒级低延迟用本地 MQ（单机共享内存+binlog，~3ms）；跨模块解耦、跨 IDC、海量积压、要求可靠才上 WQ——代价是固定多一跳网络，延迟 ~135ms。

追问储备：

  • 为什么 WQ 延迟 135ms 这么高？ → 消息要写 WFS（跨网络+落盘）才算入队成功，比本地 binlog 多了网络往返和副本同步（→ Q4 展开）
  • 本地 MQ 和 WQ 怎么选？ → 演进叙事：先本地 MQ 做模块内异步，需要跨业务/跨 IDC/海量积压再切 WQ——“两代 MQ 的取舍都有实战认知”

Q2 WQ 的整体架构是什么样的？

面试官想考什么：组件划分和职责，看你能不能把 WQ 讲成”几个角色各司其职”。

口述答案：

四个角色，拿 Kafka 对照着讲最清楚：

queuesvr（入队服务）+ broker（出队服务）——对应 Kafka 的 Broker，但拆成了入队和出队两个模块，而且两者都是无状态的：不落本地盘，数据全部写 WFS，自己只做”写文件/读文件 + 索引 + 清理”。无状态是整个架构最关键的词——扩缩容和故障恢复不用搬数据，重新挂上 WFS 就能干活。

WqScheduler——对应 Kafka 的 Controller 加 GroupCoordinator，做分区调度和消费组协调（rebalance 的发起和收敛）。

Chubby——对应 ZooKeeper/KRaft，存元数据和分布式锁。消费组的全部状态（成员、offset、分区持有关系）都在 Chubby 的目录结构里。

WFS——不在 Kafka 里对应任何角色，因为 Kafka 的存储在 broker 本地；WQ 把存储整个外包给 WFS 分布式文件系统，3 副本和容灾由 WFS 保证。

底层链路：生产者 → queuesvr → 批量写 WFS（组提交：攒一批或超阈值才真正写）→ 消费者经 broker 从 WFS 读。配套还有 file_cleaner（定期清理过期 WFS 文件，对应 Kafka 的 retention）和 file_indexer（日志索引）。

追问储备：

  • 入队出队为什么拆两个模块？ → 无状态后职责单一化，入队和出队可以独立扩容
  • 组提交是什么？ → 攒一批消息（数量或大小阈值）合并成一次 WFS 写，摊薄网络和落盘开销

Q3 消息怎么发不丢？（生产者视角）

面试官想考什么：Kafka 面试必考的”消息不丢三段论”（生产者 acks / broker 刷盘 / 消费者提交）第一段，看你能不能映射到 WQ。

口述答案：

Kafka 里生产者不丢靠 acks=all 加重试；WQ 的对应实现：

入队成功 = 消息写入 WFS 完成。WFS 本身 3 副本，queuesvr 收到消息后批量写 WFS，写成功才向生产者返回成功——所以生产者拿到成功回执时，消息已经落在 3 副本的分布式文件系统里了，queuesvr 本身崩了也不丢，因为它本地根本没存数据。

发送侧的重试和去重：生产者重试可能造成重复，WQ 支持入队去重（unique_id）——对应 Kafka 的幂等生产者。业务给每条消息带唯一 ID，服务端识别到重复就直接返回上次的成功结果。

边界要说诚实：不丢的是”已经确认入队”的消息。生产者发出后、拿到确认前如果崩了，这条消息处于未知状态——这是所有 MQ 的通病，解法要么事务消息，要么业务侧”本地消息表 + 对账补发”。

追问储备：

  • 和 Kafka acks=all 的区别？ → Kafka 是 broker 本地多副本 ISR 确认；WQ 是 WFS 写入确认（副本逻辑在 WFS 内部，对 broker 透明）
  • 重试导致的重复怎么办？ → unique_id 服务端去重 + 消费端幂等（at-least-once 语义下重复不可避免）

Q4 为什么说”把副本同步外包给 WFS”是最本质的架构分叉？

面试官想考什么：这是 WQ 面试里最有深度的一题，答出”三个连锁反应”就能和背 Kafka 的人拉开差距。

口述答案：

Kafka 的 broker 是有状态的：分区日志存本地磁盘，副本同步、ISR 维护、leader 选举全是 broker 自己管——换来通用性和极致吞吐。

WQ 反过来：数据写 WFS，副本和容灾由 WFS 保证；queuesvr/broker 无状态，只做读写转发。代码里就是拿到 WFS 路径和 group，按 partition 目录批量写。

这个分叉带来三个连锁反应：

① 扩缩容/故障恢复极简。Kafka 扩容要迁分区数据、切 leader 副本；WQ 的 broker 没有数据，挂了换一台重挂 WFS 即可，扩容同理。

② 跨 IDC 容灾天然内建。offset 在 Chubby 里按数据所在的 IDC 分开记（offset/$topic/$idc/$partition），天然支持”上海的消费者读深圳的队列”——Kafka 要做这个得靠 MirrorMaker 搭同步链路，WQ 是原生能力。

③ 代价是固定多一跳网络。所有写入都要过 WFS 这一层，WQ 延迟 ~135ms，远高于本地 MQ 的 ~3ms——这就是”外包”的价钱。

总结成一句面试话术：“Kafka 把存储、副本、协调都自己做，换来通用性和吞吐；WQ 把存储副本外包给 WFS、协调外包给 Chubby，换来无状态 broker 和内部多 IDC 生态深度集成，代价是固定多一跳网络延迟。”

追问储备：

  • ISR 是什么？ → Kafka 的 In-Sync Replicas，跟得上 leader 的副本集合，acks=all 只等 ISR 确认；WQ 没有这个概念，因为副本逻辑在 WFS 里
  • 为什么本地 MQ 只有 3ms？ → 数据在共享内存+本地 binlog，零网络开销

Q5 消费是推还是拉？

面试官想考什么：Kafka 只有拉模式，WQ 默认推模式——这是最显眼的”腾讯特色”，也最能体现你真的了解 WQ 而不是背 Kafka。

口述答案：

Kafka 是纯拉模式：消费者自己 poll，手动 commit offset。好处是消费者按自己能力拉、天然背压；坏处是空轮询浪费、延迟取决于 poll 间隔。

WQ 默认是推模式，而且形态很特别：有个 consumeragent 组件，它的 IO worker 从 WFS 拉数据、handle worker 直接回调业务的 svrkit RPC 接口。也就是说——业务不用写任何消费循环代码，只需要实现一个 RPC 接口，消息来了框架直接调你。

这个设计是腾讯内部生态的产物：业务本来就是 svrkit 模块，消费代理直接复用现有模块，零额外部署。对比 Kafka 消费者要独立进程、独立部署、自己管重平衡，WQ 把这些全收走了。

语义也清晰：消费成功 = RPC 返回 0；非 0 自动进重试；调用超时 = 代理感知后换同 group 的其他机器重试——这个”换机重试”是推模式对业务故障的容错优势，单机消费卡死不会堵住整条队列。

也有拉模式兜底：业务自己起 wqconsumer 二进制主动拉，接近 Kafka 原生消费者的用法。

追问储备：

  • 推模式不会压垮消费者吗？ → 失败进重试 + 换机，速率由 group 和分区分配约束
  • 消费位 offset 谁提交？ → agent 侧管理，业务无感知（对比 Kafka 手动 commit）

Q6 Rebalance 怎么做的？（route vs owner 是核心考点）

面试官想考什么：rebalance 是 Kafka 面试的重头戏（触发条件、过程、危害）。WQ 的实现有一套自己的”两个状态”模型，是这册里最值得背细节的题。

口述答案：

先看元数据放哪：Kafka 新版把消费组状态放 KRaft（旧版放 ZooKeeper）；WQ 放 Chubby，每个 group 一个目录，底下四个子目录：

  • members/ —— 活跃消费者 IP，内容是最近心跳时间
  • offset/ —— 消费偏移，按 $topic/$idc/$partition 分文件
  • owner/ —— 每个分区当前被谁持有（实际状态）
  • route/ —— 每个版本的分区分配结果（期望状态），$version/$ip → (idc, topic, partition)

核心模型就一句话：route 是”系统的最终状态”（期望分配），owner 是”系统的当前状态”（实际持有）。

Rebalance 的过程：触发时 scheduler 生成新版本的 route 并更新 version；此时 owner 和 route 不一致——通过心跳把分区”收回/下发”，owner 逐步收敛到 route。这就是 Kafka”期望分配 vs 实际分配”的文件版实现：不是一次性切换，而是靠心跳逐个对齐。

触发条件和 Kafka 完全一致：组成员扩缩容、机器/进程故障、心跳超时。rebalance 任务分事件触发和定期 Normal两种，失败进延迟重试队列。

分区分配算法是 WQ 的差异点：用一致性哈希而不是 Kafka 的 Range/RoundRobin/Sticky——好处是缩容时迁移的分区最少（一致性哈希的单调性）。

追问储备：

  • rebalance 有什么危害？ → 期间分区不可消费、可能重复消费（offset 未提交部分重放）——Kafka 通用知识，WQ 同理
  • 怎么避免频繁 rebalance？ → 心跳超时别配太敏感、consumer 处理逻辑别阻塞心跳
  • 为什么用文件不用内存状态？ → Chubby 天然持久化+带锁，scheduler 挂了状态还在

Q7 消息会重复吗？消费端怎么保证幂等？

面试官想考什么：投递语义（at-least-once / exactly-once）——所有 MQ 面试标配。

口述答案：

先定性：WQ 是 at-least-once（至少一次），重复不可避免。来源三个：生产者重试（网络抖动重发）、消费失败重试（同一条多次投递）、rebalance（offset 没提交的部分会重放）。

生产端去重：入队带 unique_id，服务端识别重复直接返回——把”生产者重试导致的重复”这一类掐掉。

消费端幂等是业务责任，常见做法：消息带唯一业务 ID，处理前查去重表；或以”状态机推进”设计——只有合法状态迁移才生效，重复消息自然被拒绝（比如”已处罚”状态再来一条处罚消息直接忽略）。

要不要 exactly-once？实践中不建议追求——Kafka 的 exactly-once 靠事务+两阶段提交，代价大且局限在单集群内；业界主流就是 at-least-once + 消费端幂等，把精力放在把幂等做对。

追问储备：

  • Kafka 怎么做 exactly-once？ → 事务协调器 + 幂等生产者（PID+序列号）+ read_committed 隔离级别，仅限同集群内 stream 处理
  • 去重表本身怎么扛量？ → 带 TTL（消息本身有生命周期，过期前的重复窗口有限）

Q8 事务消息怎么支持？

面试官想考什么：分布式事务里”本地事务 + 发消息”的原子性——RocketMQ/Kafka 都有事务消息，WQ 的特色是反查。

口述答案：

场景：业务要”先写数据库，成功后发消息”——两步之间如果崩了，要么消息没发出去（下游永远不知道），要么发了但数据没写（下游拿到假消息）。

WQ 的事务消息三接口：PublishTxMsg 发半消息 → 业务执行本地事务 → CommitTxMsg 提交 / RollBackTxMsg 回滚。半消息对消费者不可见，提交后才投递。

WQ 的特色是”反查”兜底：如果业务发了半消息之后既没有 commit 也没有 rollback（比如崩了），WQ 会按事务 ID 反查业务方——业务实现一个反查接口，告诉 WQ”这个事务到底成没成”，WQ 据此自动提交或回滚。

对比：RocketMQ 也有事务回查；Kafka 的事务是另一回事（多分区的原子写入，服务于 stream 处理），不是”本地事务+发消息”这个语义。

更简单的替代：本地消息表——业务把”要发的消息”和业务数据写同一个本地事务，后台任务扫表补发。笨但可靠，配合 WQ 的 unique_id 去重防重复补发。

追问储备：

  • 半消息存哪？ → 同样在 WFS，只是标记了未提交状态
  • 反查不到业务（业务也挂了）？ → 重试 + 超时兜底（回滚），细节按具体配置

Q9 顺序性怎么保证？

面试官想考什么：分区有序 vs 全局有序——MQ 的经典题。

口述答案：

和 Kafka 同一套答案：分区内有序，跨分区无序。

生产者把需要有序的消息发到同一个 partition（按业务 key 哈希，比如同一个 uin 的消息固定路由到一个分区），单个分区内按写入顺序存储、按顺序投递。

消费端维持顺序的前提：同一分区同一时刻只被一个消费者持有——这正是 owner 目录和 rebalance 机制保证的：一个分区在同一版本 route 里只会分给一个 member。

全局有序要么单分区（牺牲吞吐），要么业务层按 key 串行。一般业务只需要”同一个用户/同一个订单有序”，分区有序就够。

补充一个对照：本地 MQ 的做法是 per-uin 串行——同 uin 的任务排进等待队列，前一个完成才放下一个，不同 uin 并行。这是顺序和吞吐的经典折中，两代 MQ 殊途同归。

追问储备：

  • rebalance 期间顺序会破吗？ → 会短暂重复消费（at-least-once），但顺序不乱（offset 递增重放）
  • 热点 key 全挤一个分区怎么办？ → 分区级热点，业务侧拆 key 或接受该分区吞吐上限

Q10 延迟消息怎么实现？

面试官想考什么：延时/定时投递，实际业务高频需求（超时关单、重试退避）。

口述答案：

WQ 原生支持：PublishDelayMsgAt（指定时刻投递）/ PublishDelayMsgAfter（延迟多久投递），上限 30 天。

实现思路（通用）：延迟消息先进按到期时间组织的延迟结构，到点才转入真实 topic 分区投递。本地 MQ 的实现更经典——按 next_dispatch_time 排序的最小堆，堆顶 O(1) 拿最早到期任务，后台线程精确睡到下个到期点，新任务入队用条件变量唤醒，毫秒级精度且 CPU 几乎为零。

对比 Kafka：原生不支持延迟消息，要靠两个 topic 倒手（发到延迟 topic、定时器搬到目标 topic）或外部定时器触发——WQ 这个是原生能力，省了业务搭定时搬运的活。

追问储备：

  • 为什么上限 30 天？ → 延迟消息占存储且到期前不可清理，超长延迟用”定时任务触发发送”更合理
  • 到期精度？ → 秒级（本地 MQ 毫秒级）

Q11 积压了怎么办？

面试官想考什么：线上应急能力 + 容量规划意识——实践题，考你是不是只会背概念。

口述答案：

先定位积压的原因，三种对症下药：

消费者处理慢（最常见）：加消费者实例。但注意分区数是并发上限——消费者数超过分区数就是浪费，分区不够先扩分区。WQ 的推模式下加机器就是加 group member，rebalance 自动分走分区。

突发流量：看能不能丢弃——评估消息有没有过期语义（过期消息 file_cleaner 会清理）；不可丢的批次类消息看能否降级（比如写离线库慢慢消化）。

消费者故障/卡死：推模式的优势在这——调用超时后 agent 自动换同 group 其他机器重试，单机故障不会堵住整条队列；确认是代码 bug 就先修再放量。

容量规划（事前）：按峰值入队速率 × 平均消费耗时算需要的消费者数，再按分区数取整上限；积压水位要设监控告警，别等用户投诉才发现。

WQ 相比 Kafka 的一个积压优势：broker 无状态、存储在 WFS 弹性扩——积压本身不会压垮 broker（Kafka 积压占本地盘，盘满 broker 挂）。

追问储备：

  • Kafka 积压的坑？ → 盘满、page cache 失效读走盘、消费 lag 监控
  • 怎么估算能追平？ → 追平速率 = 消费吞吐 - 入队吞吐，积压量 ÷ 差值 = 追平时间

Q12 消息怎么存、怎么清理？（retention 对比）

面试官想考什么：存储模型和生命周期管理。

口述答案：

存储：按 partition 目录组织在 WFS 上，写入是追加写（组提交攒批）——WFS 追加写性能好，这是吞吐的根基。对应 Kafka 的分区日志段（segment）。

索引：file_indexer 维护消息位置索引，消费者按 offset 定位读取——对应 Kafka 的 .index/.timeindex 文件。

清理：file_cleaner 定期清理过期的 WFS 文件——对应 Kafka 的 retention（默认按时间/大小阈值删旧 segment）。区别是 WQ 清理的是 WFS 上的文件对象，Kafka 删的是本地日志段。

消费位：offset 记在 Chubby（offset/$topic/$idc/$partition），不在消息文件里——对应 Kafka 旧版存 ZooKeeper、新版存 __consumer_offsets 内部 topic。WQ 按 IDC 分开记又和跨城能力勾连：换一个 IDC 的消费者接着读，offset 体系天然支持。

追问储备：

  • Kafka 零拷贝？ → sendfile 从页缓存直发 socket；WQ 读要过 WFS 网络，没有本地页缓存这层优化——这是 135ms 延迟的又一来源
  • 文件多大切一个？ → WFS 对象粒度由集群配置定（Kafka segment 默认 1G）
