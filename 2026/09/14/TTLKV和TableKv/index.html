TTLkv 和 TableKv

TTLKV（Time-To-Live Key-Value）的定位是：支持 TTL 过期时间的强一致 KV 存储服务，但基于 Paxos 协议实现多副本强一致。

它是否”内存”取决于部署模式，并非天生只能是内存数据库：

部署模式 说明 是否内存
SSD 部署 标准模式，写落盘，读可能读盘 否（盘为主）
落盘全内存 内存保存全量数据，写落盘，读不读盘 ✅ 是（数据在内存）
非落盘全内存 数据在 tmpfs 上 ✅ 是（极致性能）

TableKV一种基于持久化存储引擎（LevelDB / LSM-Tree）的分布式强一致 KV 存储服务，对外提供类似 MySQL 二维表的操作接口。

  • 存储引擎：TableKV（table kvsvr）以 LevelDB 为底层存储引擎。LevelDB 是 Google 开源的持久化 KV 系统，采用 LSM-Tree（Log Structured Merge Tree） 结构，数据落盘，并非内存存储。
  • 一致性：在 LevelDB 之上实现了 Paxos 协议，保证分布式环境下的多副本强一致。
  • 数据模型：提供类似 MySQL 的二维表接口（Select / Insert / Update / Delete），支持二级索引、唯一索引，每张子表有主键。底层仍是简单 KV，复杂查询依赖索引回表。

TTLKV

TTLKV 是什么

TTLKV 是一个强一致、高性能的分布式键值存储系统，用 Paxos 协议保证一致性，底层存储引擎是 leveldb/rocksdb（LSM-tree，落盘的），支持按 TTL 过期淘汰。

适用：需要过期淘汰的强一致 KV 读写；可全内存部署也可非全内存部署；key 最大长度 1000。

**不适用：

  • 大量 key 的定时批量更新、最终一致 → 用 featurekv
  • 离线场景下的大量写入 + 顺序扫描 → 用 wbt

ttlkv、redis、mysql的区别

总揽的说下：

  • Redis 是内存数据库——数据在内存、异步持久化，追求的是极低延迟（微秒级）。定位是缓存和轻量数据结构服务。
  • MySQL 是关系型数据库——B+树索引、SQL、多表 join、完整的 ACID 事务。定位是需要复杂查询和强事务的业务主存储。
  • TTLKV 是分布式强一致 KV 存储——底层是 LSM-tree 落盘、一致性是 Paxos 多数派。

下面同个几个维度进行对比：

1、数据存在哪

Redis 在内存——所以快，但受内存容量约束，成本按内存算；持久化是 RDB 快照 + AOF 日志，是异步的补充手段，不是主存储路径。

MySQL 在磁盘（InnoDB Buffer Pool 做缓存），B+树结构，数据落盘是主路径。

TTLKV 在磁盘（leveldb/rocksdb，LSM-tree），但可以全内存部署——数据放 tmpfs、不落盘。所以它容量弹性比 Redis 好：需要极限性能就全内存部署，需要大容量就落盘。

2、一致性

Redis 主从是异步复制——主写完立刻返回，还没同步到从。主挂了、从提升为主，最后一段写入就丢了。Cluster 模式的分片之间也没有多数派共识。所以 Redis 的定位注定是”可以丢一点”的场景。

MySQL 单机是强一致的（redo log + WAL + fsync），但主从复制默认也是异步的——半同步复制能改善，但要真正不丢就得上 MGR 或者外部一致性方案。单机强一致、集群层面要额外做。

TTLKV 是 Paxos 多数派落盘（可切 Raft）——写成功即多数派已持久化，就是不丢。这对支付、账号这类场景是硬需求。而且读侧还是分级的：强一致读要去多数派确认，最终一致读（skip_paxos）直接读本机、性能更高。

3、查询能力

MySQL 最强：SQL、多表 join、聚合、子查询、任意维度的二级索引、优化器自动选执行计划。想怎么查就怎么查。

Redis 最弱：只能按 key 访问，没有二级索引、不能按 value 条件查。想按其他维度查只能业务自己维护反向索引。

TTLKV 也是按 key 访问，同样没有二级索引——但比 Redis 多了一些：原生 Protobuf 读写（可以操作 PB 的嵌套字段）、JSON 节点查询修改、TimeSeries 按时间粒度聚合。

4、事务能力

MySQL 完整 ACID——多表、多行、可回滚、有四种隔离级别、MVCC。

Redis 的”事务”很弱：MULTI/EXEC 只保证命令打包顺序执行不被打断，不支持回滚——中间某条命令失败，前面的照样生效。真要原子逻辑得写 Lua 脚本。

TTLKV 是”单 key 原子”，加上一个特殊能力：多 key 分布式事务。另外它把高频的事务型业务模型直接做成了原生接口——比如 balancekv（余额修改 + 流水记录强一致事务），这个用 Redis 就得自己拿事务加 Lua 拼。

怎么做分布式

怎么分片、怎么路由和副本

分片：按 key 哈希分到 PG（Partition Group）。 每个 PG 是一个独立的一致性组，组内多副本分布在不同机器、不同园区。不同 key 的写落在不同的 Paxos 组里，完全并行互不干扰。能横向扩写吞吐的根本，和整个集群一个共识组的设计相比并行度差一个量级。

路由：由 proxyserver 集中管理。 client 拿到一个 key，先哈希定位到 PG，再从 proxyserver 那里拿到这个 PG 的副本分布，直接访问对应机器。机器故障时 proxyserver 自动屏蔽故障机、切换路由，client 完全感知不到。

副本：DB 三副本 + Paxos 五副本。园区上一般是六园区部署，容忍双园区故障。

扩缩容靠调度系统：副本可以跨机器迁移（拷数据 + 切路由），紧急扩容时可以让 Paxos 副本和 DB 副本同时转移。整个过程对业务透明。

追问：为什么不用一致性哈希环，让客户端自己算？

PG 模型下路由是 proxyserver 集中管理的，扩缩容变成”调度系统迁移副本 + 更新路由”，比客户端哈希环灵活得多——比如可以按热点动态给单个 key 加代理副本（REQUEST_PROXY），客户端哈希环做不到这种细粒度调度。

怎么实现分布式一致性/强一致性怎么保证

写路径靠 Paxos 多数派落盘，内部组件叫 certain，新架构可选 Raft。

核心抽象是 Entity 和 Entry：对 ttlkv 来说一个 key 就是一个 Entity——也就是一个独立的一致性单元；一次写操作是一个 Entry，走一轮 Paxos 达成多数派。存储上分两层：协议日志是 PLog，数据落 DB（leveldb/rocksdb）。流程是先过 Paxos 达成一致写 PLog，再异步应用到 DB——PLog 是 WAL 性质的，DB 落后了就靠 PLog 追齐。

读侧的一致性是分级的

  • 强一致读：要去多数派确认数据是不是最新的；
  • 最终一致读：直接读本机 DB ，靠写入时的实时同步（毫秒级）+ 每 60 秒全量对齐兜底，默认保证和强一致读的差距不超过 10 秒（可配）

协议还能切 Raft：性能提升 30~40%，但代价是单机故障时会出现短暂的最终失败（强 Leader 切主期间不可写），所以只推荐给对可用率要求没那么极致的模块。这个取舍能说明”新协议不一定更好”。

追问：最终一致读有什么风险？

极端情况下落后不是 10 秒而是几小时。因为它依赖实时同步，如果某台机器硬盘满了、或者过载导致同步卡住，这台机器可能落后几小时甚至一天，读到的就是很旧的数据。如果 FinalConsistencyLagThreshold 配得太短、或者业务请求量太少，会退化成强一致读——每次读还是要去多数派确认。

高并发下单key问题如何解决

单 key 问题要分读热和写热，两者的天花板完全不同

先说读热

第一层是服务端请求合并。 ttlkv 单机会把同一个 key 的并发请求合并成一次处理——一万个请求打同一个 key，底层只查一次 DB。配置项就是 MergeReadReq
第二层是加副本扩读。 只读副本可以部署多个，client 随机访问不同副本；只读副本还能换用 hashdb 引擎——纯哈希结构没有 LSM 的层次，点读更快
第三层是自动伸缩副本。 ttlkv 会持续检测单 key 的读 QPS，超过阈值自动加副本，QPS 降下来持续一段时间后自动减副本，完全不用人工干预。
第四层是 REQUEST_PROXY 请求代理副本，对付极端热点。思路是在 client 和真正的 ACCEPTOR 之间插一层代理，代理把大量打同一个 key 的请求合并后再转发，从而保护后端。

写热，这个是物理上躲不掉的。 因为一个 key 就是一个 Entity、也就是一个一致性单元，同一个 key 的写会被 Paxos 串行化——所以单 key 写吞吐有天花板，加副本、加机器都没用。

拆 key（比如计数分成 N 个桶分别累加、读的时候聚合，把一个热 key 变成 N 个温 key）；走 UDF——用 Calc 接口把计算下推到 server 端，网络上只传增量；或者业务侧攒批，前端聚合一段时间再写一次。

value 存多大性能会急剧下降？

16KB 左右是存储引擎层的分离线。 leveldb 的 big-value 分离阈值一般配在 16399 字节，也就是约 16K，超过就旁路存储、不参与正常的 compaction。有需要还可以降到 8K 甚至更小。

32KB 是应用层 objstore 的默认分离阈值。 超过 32KB 的 value 自动写到 objstore 模块，ttlkv 里只留一个索引，读的时候 client 自动回源拼装。适用范围是 20KB 到 100MB 的写多读少场景。

4MB 是单 value 的建议上限，超了直接写入失败。

为什么大 value 会急剧劣化，三个原因： ① 写放大——LSM-tree 的 compaction 要反复搬运数据，value 越大搬的字节数越多，一次写实际产生的磁盘 IO 是数倍； ② 缓存被挤占——大 value 吃掉 block cache 和内存，把别的 key 的命中率一起拖累； ③ Paxos 协议开销——value 要跟着协议日志在多个副本间同步，网络和落盘成本都按 value 大小线性放大。

支持哪些数据结构？

基础组：string（支持 CAS 和多版本）、hash（字段级增删改查）、list、set、hyperloglog（基数估计）、json（可查询修改节点）、Protobuf（原生 PB 对象读写）。

计数统计组：int 接口（原子增减 Incr）、TimeSeries（按秒/分/时粒度聚合）、seqsvr/idmaker（单调递增序列号、分布式唯一 ID）。

业务模型组：balancekv 余额+流水强一致事务、quotakv 单维/多维限额、ratelimitkv 分布式限流、分布式并发锁。

架构组：cachekv 回源缓存、objstore 大 value 存储、HyperStore 高性能架构。

副本怎么部署？容灾能力怎么样？

TTLKV 的部署形态是 DB 三副本 + Paxos 五副本，这个分离本身就是个设计点：Paxos 五副本用于投票，多数派 3/5 能容忍双机同时故障仍可写入；数据只存三副本省 40% 存储成本。可降级到三副本（调度操作）。

容灾矩阵按副本数：2 副本容忍单机/单园区故障，3 副本容忍双机/双园区故障。副本跨园区分布，所以”双园区故障”也覆盖了。

副本类型还有三种特殊形态，各有用途：
只读副本——不参与写，专吃读流量，可用不同存储引擎（leveldb 或 hashdb）；
filter 副本——按前缀只存部分数据，把大集群的 BatchGet 聚集到一台机器上，解请求放大（实测 CPU 从 6000 降到 4100，线上案例平均 batch 从 4.1 涨到 108）；
HotBackup 热备副本——专门做流水导出（CDC）和跨城同步，不扛线上流量。

追问储备：

  • 为什么 Paxos 五副本数据三副本不会不一致？ → PLog 五副本保证共识，DB 三副本是共识结果的落地，落后了靠 PLog CatchUp
  • REQUEST_PROXY？ → 热点 key 的代理副本，本地无 DB、调度秒级完成（主题库 Q60 详述）

Q6 读性能怎么扩展？

面试官想考什么：读路径的分层设计能力——这题最能体现 TTLKV 区别于”加从库”的思路。

口述答案：

读扩展有三级，按侵入性从小到大。

第一级：最终一致读（skip paxos）。正常读要过 Paxos 校验数据最新性；开启 skip_paxos 后直接读本机 DB，不过协议。适合缓存类场景——默认保证与强一致读的差距不超过 10 秒（可配），数据更新靠写入实时同步（毫秒级）+ 每 60 秒一轮全量对齐兜底。性能收益明显：单 key 读 230W qps 提到 265W（+15%），批量读 +39%。风险要主动说：极端情况（某台机器硬盘满、过载）同步卡住，这台机器可能落后几小时甚至一天，读到的就是旧数据——所以不能无脑全开。

第二级：只读副本。DB 三副本扛不住读就加只读副本，一个 kv 可以部署多个；可以用 hashdb 引擎（纯哈希无 LSM 层次结构，点读更快）；client 还支持优先访问只读副本做读写分离。

第三级：filter 副本。针对 BatchGet 请求放大——大集群里一次 BatchGet 会均摊到很多台机器。filter 副本按前缀把数据聚集到一台机器，请求就集中了。

还有配套的轻量读容易被忽略：它优化的是一致性协议判断的 CPU 开销而不是延迟——开启后用多副本随机读降低冲突。有个硬性搭配：跨城只读副本必须配轻量读，否则 Paxos 冲突会很严重。

追问储备：

  • skip_paxos 怎么用？ → 代码 client.SetSkipPaxos(true)（注意不是线程安全的，不能多线程共用 client）+ client 配置打开才生效
  • 一致性级别能按 key 配吗？ → 能，FinalConsistencyModeByKey/P ByPrefix，比如 mmtest_1:1,mmtest_2:2

过期淘汰怎么实现

接口层面：Set 时带 lifetime 参数（秒），0 表示永不过期。有个坑要记：第一次设了过期时间，第二次 Set 不带 lifetime，会沿用上一次的过期时间，不是改成永不过期——想改永不过期要走 BatchSet 的 set_new_life_time 参数。

实现层面走的是 LSM-tree 的 compact（压缩） 时丢弃：过期数据不立刻删，leveldb/rocksdb 做 compaction 时发现已过期就直接不写入新层，等于”随压缩顺带清理”。平时写入触发部分 compact，每天凌晨 1 点全量 compact 一轮

追问储备：

  • Get 一个已过期但没 compact 的 key？ → 返回 not found，过期判断在读取时也生效，compact 只是物理清理
  • 过期时间和版本能共存吗？ → SetLifeTime 接口单独改过期时间，支持 version 校验

底层存储引擎为什么用 LSM-tree？

面试官想考什么：LSM vs B+树这个经典问题，能不能结合自己的存储讲。

口述答案：

底层是 leveldb/rocksdb，LSM-tree 架构。选它的核心原因是写友好：写入只追加到内存 memtable + 顺序写 WAL 和 SSTable，没有 B+树那种原地更新的随机写。而 KV 负载——尤其 TTLKV 有大量带 TTL 的中短生命周期数据——写入量远大于更新量，LSM 的 compact 顺带就把过期数据清了，特别契合。

代价是读放大（要查多层）和 compact 的写放大，工程上用 BloomFilter、block cache、分层 compaction 来压。

两个具体演进：一是 rocksdb 替换 leveldb，读写 QPS 均有约 20% 提升（读用了 io_uring）；二是 rocksdb 的一些特性被 TTLKV 直接吃掉——Merge 操作实现 Read-Modify-Write，计数器 Incr 不用先 Get 再 Set，特别适合 SetPB 的部分更新，不用每次读写完整 PB；BlobDB（WiscKey 思路）做大小 value 分离，正是 objstore 的理论基础；Column Families 共享 WAL 支持跨 CF 原子写。

追问储备：

  • hashdb 是什么？ → 只读副本可用的另一种引擎，纯哈希结构无层次，点查更快
  • 四种架构怎么选？ → HyperStore 极限吞吐但不支持 CAS（写 2000W key/s）；Table4 范围路由可扫描；Aurora 租约强一致可运行时热切；ObjStore 大 value

Q10 大 value 和热点 key 分别怎么处理？

面试官想考什么：两个经典 KV 问题的工程解法。

口述答案：

大 value 走 objstore 自动分离。client 配置 value_size_thresh=32768（超 32KB 的 value）加灰度比例 save_ratio，大 value 自动写到 objstore 模块，ttlkv 里只留索引；读的时候 read_use_objstore 自动取回。还支持按前缀控制（prefixs / black_prefixs，与比例是”与”的关系）。适合 20KB~100MB、写多读少的场景，100KB value 单机写吞吐 2W key/s。有个部署坑：objstore 的 cli 路径必须带 idc 且和 ttlkv client 同 idc。

热点 key 分读热和写热。读热用三级火箭（只读副本/filter 副本/REQUEST_PROXY）；写热是硬上限——单 key 写被 Paxos 串行化，这个物理上躲不掉，只能拆 key（分桶计数再聚合）或走 UDF（Calc 接口把计算下推到 server 端，网络只传增量）。

追问储备：

  • UDF 接口？ → Calc(udf_id, ...) 把逻辑推到存储端执行，read_only_udf 只读安全
  • 多版本历史读？ → iVersionToKeep 保留最近 N 版（上限 1000），GetHistoryVersion 读指定版本；坑：compact 后旧版本可能拿不到，Delete 不清历史版本

Q11 CAS 和分布式锁怎么做？

面试官想考什么：并发控制的两个标准武器在 TTLKV 上的形态。

口述答案：

CAS 靠 version 机制，语义有三个精细点：
① Set 传 version，服务端只允许写入相等的 version，成功后 version+1，不匹配返回 -110202；
② 第一次写传 NULL 不比较、多个并发都成功；传 0 则比较版本、只有一个成功——这就是”只初始化一次”的标准做法；
③ 失败时也能拿到最新版本号（new_version 出参），方便读-改-写重试循环。
注意 HyperStore 架构不支持 CAS（只支持覆盖写）——选架构时的一致性能力差异。

分布式锁是原生能力（基于 hash 结构），支持 tryLock、续期、释放。对比自己用 Redis SETNX 拼：TTLKV 的锁带强一致语义，主从切换不会丢锁。另外还有”基于 Hash 能力实现分布式并发限流”的封装。

追问储备：

  • CAS 的 ABA 问题？ → version 单调递增不复用，天然防 ABA（version 只会增加）
  • 锁的可用性？ → Paxos 强一致，多数派存活即可用，无 Redis 红锁的多数实例问题

Q12 性能和容量怎么评估？

面试官想考什么：上线前的容量规划意识。

口述答案：

容量公式：key_num × (40 + avg_key_size + avg_value_size) × 3 × 1.1——每个 key 约 40 字节元数据开销，×3 是三副本，×1.1 是冗余水位。

性能基准（要记得数量级和条件）：

  • 落盘全内存、value 128B：单机写 4.7w/s、读 15w/s
  • 不落盘全内存（tmpfs）：单机写 5w/s、读 20w/s——注意不落盘只是省了刷盘开销，Paxos 网络往返还在
  • 读写 1:1、value 1600B、一组 6 台：不落盘 22.2w/s
  • 读写比例对吞吐影响极大，评估必须按自己的真实读写比折算

降延迟开关的收益：skip_paxos 单 key 读 +15%、批量读 +39%；Raft 比 Paxos +30~40%。

四个架构的天花板：HyperStore 写 2000W key/s（不支持 CAS）、Table4 RangeGet 7383W key/s、Aurora 写 75W、ObjStore 大 value 2W/s——选型时先看自己要不要 CAS、要不要扫描，再谈吞吐。

追问储备：

  • key 有长度限制吗？ → 最大 1000 字节
  • 怎么压测？ → 有专门性能测试文档和工具，上线前联系 kv_helper

TableKV

TableKV 是什么？

TableKV 是一个分布式表格存储，提供类似 MySQL 的二维表操作——Select / Insert / Delete / Update，支持二级索引和唯一索引，底层是 leveldb（LSM-tree，落盘的）。

最贴切的对标是分库分表的 MySQL：它把”分库分表 + 主从复制 + 索引维护”这些 MySQL 生态里要中间件拼装的东西做成了原生能力，并且用 Paxos 替代了异步复制。

三层概念对齐 MySQL：tableid ≈ 表结构定义；uin ≈ 物理分表（不同 uin 数据完全隔离，说的”单表并发””单 key 并发”都指 uin）；主键 ≈ 分表内每行的 key（分自增/非自增）。

Q1 和 MySQL 比，TableKV 强在哪、弱在哪？

面试官想考什么：技术选型的两边都能说——只会吹自研好说明没想清楚。

口述答案：

强在四点：
① 一致性。MySQL 主从异步复制、主从切换可能丢数据；TableKV 写走 Paxos 多数派，写成功即三副本一致。
② 水平扩展内建。按 uin 天然分片，扩容是调度系统自动迁副本，不用业务层搞分库分表中间件。
③ 索引与数据同事务。索引和记录在同一个 WriteBatch 写入，不存在”索引和数据不一致”的窗口。
④ 运维体系。表结构变更、索引变更走需求系统自助流程，监控上报都是平台级。

弱在四点（主动说出来反而加分）：
① 没有 SQL 的完整性——不支持 join、复杂子查询有限（新 SQL 引擎在补，但仍是 PostgreSQL 子集）；
② ACID 范围是单表（table_id + uin），跨表事务要专门的多表事务方案，不像 MySQL 单库内随便跨表；
③ 单次查询限制 20M 或 2 万行，没有 MySQL 那种大结果集游标；
④ 单条记录上限 10MB、单次写入总 20M——它是 OLTP 形态，不是分析型存储。

一句话总结：MySQL 是功能全的单机关系模型加周边拼分布式；TableKV 是原生分布式但砍掉了关系模型的边角。OLTP 高并发点查场景它赢，复杂分析场景别用它。

追问储备：

  • 那要 join 怎么办？ → 业务层聚合；或 Sqlsvr 跨表跨组件查询（新能力，计算下推）
  • 和 HBase 之类比？ → HBase 是宽表稀疏模型无二级索引；TableKV 有完整二级索引和类 SQL 接口

Q2 一行数据的写入路径是怎样的？

面试官想考什么：写路径 + 路由 + 副本协议一条龙，分布式存储的核心链路。

口述答案：

前提是相同 uin 的请求——包括不同 tableid——会路由到同一组机器（一组 6~60 台）里的三台 A/B/C，分布在不同园区。这叫 uin 亲和，是整个设计的根基。

写路径四步：
① client 根据 uin 定位到这一组，动态路由由 proxyserver 管理，机器故障自动屏蔽切路由；
② 写请求优先访问 A 机（主副本）；
③ A 机把这次写（记录 + 索引项打包在同一个 WriteBatch）通过 Paxos 写入三台，多数派成功即返回；
④ 落盘 leveldb。

读路径不同：随机访问 A/B/C 三台中的任意一台——因为三副本数据一致，随便读哪台都行，天然打散读流量。如果某条数据读成热点了，自动增加只读副本把请求分到更多机器。

副本数是 5+3：Paxos 协议五副本（多数派 3/5，容忍双机故障仍可写）、数据存储三副本——投票方多份数据少存，一致性和成本兼得。

ACID 就落在这里：单表（table_id+uin）内保证 ACID，靠的是”Paxos 原子提交 + 记录索引同 WriteBatch”。

追问储备：

  • 为什么写必须走 A 机？ → 同一 uin 的写要串行化保证顺序一致性，固定主副本是最简单的串行点
  • A 机挂了？ → proxyserver 屏蔽并重新选主，Paxos 多数派（还有 B/C/D/E）继续工作，不丢数据
  • 跨城怎么办？ → Infinity 跨城读写最终一致方案，自增主键表要配 ReplicationIndexID 判断记录唯一

Q3 索引在底层是怎么实现的？（对比 B+树必考）

面试官想考什么：这是 TableKV 最核心的原理题——索引不是 B+树，是 LSM 里多存一行 key。答出这个，说明真理解了”索引即数据”的 LSM 哲学。

口述答案：

和 MySQL 完全不同：MySQL 索引是独立的 B+树结构；TableKV 的索引就是 leveldb 里额外存的一行 key——索引即数据。

拿例子说。表有主键 F1，定义了索引 Index3=4 5（F4、F5 两列）。那么每条记录在 leveldb 里存不止一行：

  • 数据行：key = {uin, tableid, 0, F1的值}，value = 完整的记录数据
  • 索引行：key = {uin, tableid, 3, F4的值, F5的值, F1的值}，value 为空

三个设计点：
① 索引行末尾拼上主键——保证索引 key 唯一（不同记录的 F4F5 可能相同，拼了主键就不撞）；
② 数据行和所有索引行在同一个 WriteBatch 原子写入——这就是索引和数据永不不一致的实现；
③ 索引行的排列天然按索引列有序——因为 leveldb 的 key 全局有序，等值/范围查询就是前缀定位 + 顺序扫描，没有树查找；要拿完整记录就是从索引行里取出主键再 MultiGet 一次（相当于回表，但叫 MultiGet）。

代价：每条记录每加一个索引就多写一行 key，写放大直接乘上去——所以索引不是越多越好。一个 Index3=4 5 的开销约 28 字节 + F5 长度。

一个类型陷阱：字符串列（V 类型）在索引 key 里的编码是”长度+内容”，不构成字典序，所以 V 类型索引只能做等值匹配，做不了范围查询（新架构的 LexicalIndex 在补这个）。

追问储备：

  • 为什么 leveldb 能这样玩？ → LSM 的 key 全局有序 + 范围扫描原生支持，索引行只是”精心设计的 key 编码”
  • B 类型字段？ → 二进制不能用于建索引
  • 唯一索引怎么实现？ → UniqueIndex 编码进 key 前缀，插入时同 key 冲突即违反唯一性

Q4 为什么用 LSM-tree 不用 B+树？（结合自己的存储）

面试官想考什么：经典对比题，但结合 TableKV 场景答才有区分度。

口述答案：

B+树就地更新、读稳定，但写入是随机 IO（更新中间层的页）；LSM 把写变成纯追加——memtable 加顺序写 SSTable，写吞吐高一个量级。

TableKV 的负载画像决定了 LSM 更合适：
① 写多读少或写读均衡的 OLTP——点查为主，LSM 的读放大（多层查找）靠 BloomFilter 压得住；
② 索引行让写放大的大头在 LSM 里反而更顺——B+树方案下索引是独立树，写 N 个索引就是 N 次随机更新；LSM 方案下是 N 行顺序追加；
③ 过期数据零成本清理——TableKV 支持 ExpireDays / 接口级 expire，compact 时直接丢弃过期数据，B+树要单独删行。

工程细节上 TableKV 走 leveldb，TTLKV 新架构在换 rocksdb（读写 +20%，读用 io_uring）。每天凌晨 1 点一次全量 compact——把读放大和过期清理都收敛到低峰期处理。

追问储备：

  • LSM 的读放大怎么压？ → BloomFilter 判层、block cache、compact 合并
  • compact 对线上影响？ → 平时写入触发增量 compact，全量固定在凌晨 1 点，避开高峰

Q5 索引怎么选择？为什么有时候不走索引？（对比 MySQL 优化器）

面试官想考什么：等价于 MySQL 的”explain 和索引失效”，但 TableKV 的规则有自己特色。

口述答案：

六条规则，前三条和 MySQL 神似，后三条是 TableKV 特色。

① 条件顺序无关：查询条件会自动按索引顺序重排——F1=a and F2>b 和 F2>b and F1=a 完全等价，不用像写 MySQL 那样注意 and 的顺序。

② 最左前缀匹配：复合索引 2 3 4，条件必须从 F2 开始连续匹配才能用；被隔断的列终止匹配。

③ 等值放前面：建索引时等值查询的列放左边，一开始就能过滤掉大部分数据。

④ 多索引按”选择性”竞争：同时有 Index1=3 和 Index2=2 4 时，比较两个索引命中后的扫描范围比例，选范围小的——和 MySQL 优化器选区分度高的索引同理。

⑤ ⭐ 33% 退化规则（最有特色）：如果最优索引也要扫超过 33% 的数据，优化器直接放弃索引，改走主键顺序全表扫。逻辑是：走索引 = 扫索引行 + 拿主键 MultiGet 随机读完整记录；全表扫 = 纯顺序读。顺序读性能远高于随机读，扫三分之一以上时随机读的代价就反超了。这个 1/3 就是顺序读和随机读的成本平衡点。

⑥ 命中第一个范围条件后，后面的列只能过滤不能缩小范围——因为索引 key 在第一个范围列之后就不再有序了。

验证用 ExplainMsg 打印实际选中的索引——被问”你怎么确认走没走索引”，这就是标准答案。

追问储备：

  • 怎么知道索引建多了拖累写？ → 每索引一行 key 的写放大；监控里有索引维护的上报
  • 线上踩坑案例？ → 有专门的风险工单指引：select 实际读盘超结果集 10 倍、大量无效读盘、limit 过大触发查询限制——都是索引设计不当的现网案例
  • use index / ignore index？ → 新 SQL 引擎支持（语法借鉴 MySQL），但注意都只是裁剪候选数组而非强制指定，完全不匹配会退化全表扫

Q6 同样是 limit 100，为什么有的查询快有的慢？（order by 优化）

面试官想考什么：这是 TableKV 最精妙的一道题，考”索引序是否天然满足 order by“。

口述答案：

本质一句话：如果索引 key 的排列顺序天然就是你要的 order by 顺序，limit 才真正省事；否则 limit 不减少任何扫描量。

索引 Index2=2 3 4，key 排列是 F2、F3、F4 的字典序。对比三种查询：

快：where F2=x and F3=y order by F4 limit 100。F2F3 等值定位后，剩下的排列天然按 F4 有序——直接取前 100 个索引行、MultiGet 100 条，完事。limit 真省了。

慢：where F2=x and F3=y order by F6 limit 100。F6 不在索引里——必须扫出所有满足条件的行、全部 MultiGet 出来、内存排序、再取前 100。满足条件的有 10 万条就得查 10 万条，limit 形同虚设。

慢（更隐蔽）：where F2=x and F3>=y1 and F3<=y2 order by F4 limit 100。F3 是范围条件，此时索引行的排列是按 F3 有序而不是 F4——还是得全扫出来按 F4 重排。

从这推出建索引的指导原则：复合索引顺序 = 等值列 → order by 列（第一个范围列）→ 其他范围列。如果范围列和排序列不是同一个，”提前 limit”和”范围缩小”就不可兼得，要做取舍——比如把排序列放范围列前面（Index3=2 4 3），能提前 limit 了，但范围条件就只能扫出来过滤，可能扫一万条凑不齐 100 条直接返回失败。

追问储备：

  • 这和 MySQL 有什么不同？ → MySQL 索引序同理，但 MySQL 有 filesort 和优化器提示兜底；TableKV 是纯索引序规则，规划错了就是慢
  • 分页翻深页？ → 单次限制 2 万行/20M，深翻页用”记住上次位置”的游标式查询，别用 offset

Q7 事务支持到什么程度？

面试官想考什么：ACID 的边界——说”支持事务”太模糊，说清”哪里支持哪里不支持”才是真懂。

口述答案：

分三层，边界必须说精确。

第一层，单表内天然 ACID——“单表”的定义是 table_id + uin。单次批量写多行、或一次写同时改记录和索引（必然），都在同一个 WriteBatch、同一次 Paxos 提交里，原子且一致。隔离性来自单 uin 的写串行化（都走同一主副本）；持久性来自多数派落盘。

第二层，多表事务——跨 table_id 或跨 uin 就超出单 WriteBatch 能力了，要走专门的 Tablekv 多表事务方案（有专门文档）。需要时要评估，不是白送的。

第三层，跨组件事务——TableKV 之外再混别的存储，没有分布式事务，业务自己用消息队列做最终一致。

对比 MySQL：MySQL 单库内跨表事务白送（undolog+锁），TableKV 的便利边界收窄到了单表。代价换来的是：单表内的 ACID 是 Paxos 级别的强一致，主从切换不丢；MySQL 半同步复制也做不到这个强度。

追问储备：

  • 单 uin 的并发写会怎样？ → 串行排队，有单 key（uin）并发上限——高并发写同一个 uin 是反模式
  • 自增主键和唯一索引的约束？ → 自增主键表做跨城同步时要指定 ReplicationIndexID（一个不可变的唯一索引）作为记录身份

Q8 并发控制怎么做？CAS 的坑

面试官想考什么：乐观并发在无锁分布式存储上的实现细节 + 精确的踩坑经验。

口述答案：

接口自带的是 uin 维度的版本号：Insert/Update 可带 version，冲突返回 6000。注意这是 uin 粒度的——同一个 uin 的任何并发写都容易撞 6000，粒度太粗。

业务要行级 CAS，自己加一列版本号，经典模式：

update set x=1, version=y+1 where 主键=k and version=y

对应到 API：clsRecordUpdate.SetUint64(field_version, y+1) 加 clsFilterSet.AddRuleUint64(field_version, NEqual, y)。

⭐ 最大的坑（能说出来就是实战经验）：Update 的 filter 条件不命中时函数返回 0，不返回失败！version 已被别人改成 y+1 的话，这次 Update 静默地一行没改。必须检查 result_list->GetSuccessCount() > 0 才知道 CAS 到底成没成。多少人在这上面翻车——看起来 CAS 成功了，实际什么都没写进去。

追问储备：

  • 为什么 filter 不命中不报错？ → Update 语义是”改所有满足条件的行”，0 行满足也是合法结果
  • 悲观锁有吗？ → 没有 MySQL 那种行锁；单 uin 写天然串行可当粗粒度悲观锁用

Q9 过期数据怎么删的？

面试官想考什么：和 MySQL 删行对比，考 LSM 的 lazy delete 理解。

口述答案：

两种配置：表级——tabledef 里 [SDBCONF_表名] ExpireDays=1；接口级——Insert/Update 传 iExpireTime（相对秒数），优先级高于表级。

一个坑：Insert 时指定了过期时间、Update 时没带，这条记录就回退到表级配置；表级也是 0 的话就变成永不过期了——本来想续期的，结果变成永久，方向完全反了。

删除机制是 LSM 特色的 lazy delete：过期那一刻什么都不发生，读取时判断过期返回 not found（逻辑删除）；物理清理靠 compact 时直接丢弃——写入触发增量 compact，每天凌晨 1 点全量 compact。对比 MySQL 的 DELETE 是即时删除事务+binlog，TTL 场景下 TableKV 这套的清理成本约等于零。

追问储备：

  • 过期前能查到吗？ → 能，接口能拿到剩余时间，业务可感知临近过期
  • 大量同时过期？ → 清理压力在 compact 侧、分散在平时，不会像 MySQL 那样瞬间大量删行

Q10 容量和并发有什么限制？（背数字）

口述答案：

五个数字：
① 单条记录 ≤ 10MB；单次写入多记录总 ≤ 20M——它是 OLTP 不是大对象存储；
② 单次查询遍历 ≤ 20M 或 2 万行（20M 指所有字段总和；遍历索引则算索引字段）——防大结果集拖垮；
③ 单 uin 记录数无限制，总量受磁盘（TS80A 1.5T / IT5 3.5T）；
④ 单 key（uin）并发有限制——同 uin 写串行，高并发写同一 uin 是反模式；
⑤ 字符串字段不能含 \0（会被截断），V 类型不能做范围索引。

排查套路：返回 -1/-2 先查两件事——测试环境配置是否更新、是否加载了多个 tabledef 文件。

追问储备：

  • 超过了怎么办？ → 大记录拆字段/拆表；大结果集改游标分页多次拉
  • tabledef 是什么？ → 表结构定义文件（字段/类型/索引），全局配置；结构上线后不能改，只能加字段/索引——测试环境也是改了就换新 tableid

Q11 扩容怎么扩？和分库分表比好在哪？

面试官想考什么：水平扩展的运维形态——“原生分布式 vs 中间件拼装”的差别。

口述答案：

MySQL 分库分表的扩容是业务侧的痛：加机器要迁移数据、改分片路由、双写切流，中间件和业务都参与。

TableKV 的扩容是存储系统内部的调度：
① 单园区扩容——调低该园区（sect）权重，调度系统优先把 Paxos 副本迁出去，副本转移顺序可选（紧急时 Paxos 和 DB 同时迁）；
② 部署新机扩容——新机器加入集群，调度把 PG 副本均衡过去，client 路由由 proxyserver 自动更新，业务完全无感；
③ 有 PG 标签机制防止副本迁到非预期的园区/sect（跨城模块、全局索引模块要按标签走）。

也有加速手段：副本粒度规划拷贝任务、”流量快速转移”——一个目的端副本拷完就把流量切过去、”首任务优先”——保证每个 PG 尽快有一个副本先完成。

一句话：分库分表把分布式的复杂度给了业务，TableKV 把它收回到存储层——代价是业务要接受它的接口和限制。

追问储备：

  • 全局索引？ → 跨 uin 的索引独立成 PG；部署后建议从 Paxos 切 Raft 提性能（+30~40%），切之前要把 leader 转移好再重启
  • 大模块拆分？ → 按 tableid/prefix 迁到全新集群，走”存量复制→双写→切流”流程，以周为单位

收尾：一句话总纲

对标分库分表的 MySQL：tableid 是表、uin 是物理分表；同 uin 亲和一组机器，写走 A 机 Paxos 三写、读随机三台、热点自动加只读副本、Paxos 五副本数据三副本。底层 leveldb，索引就是多存一行 key（索引列拼接+主键，value 空），与记录同 WriteBatch。索引六规则：最左前缀、等值在前、选择性竞争、33% 退化全表扫、范围条件后只能过滤；order by 列必须紧跟等值条件落进索引，limit 才真省。ACID 到单表（tableid+uin）；CAS 要自己加版本列，且 Update 不命中 filter 返回 0、必须查 GetSuccessCount；过期靠 compact 顺带丢弃（凌晨 1 点全量）。
