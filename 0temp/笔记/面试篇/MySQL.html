行溢出，Mysql怎么处理？

磁盘和内存交互的基本单位是页，一个页大小为16K，也就是16384字节，一个varchar最多65535字节（text blob更多），一个页不够存储就会发生行溢出，数据会存到溢出页

compact发生行溢出的处理：真实数据处保留20B存储溢出页的地址

Dynamic、Compressed处理：数据页只存储溢出页地址

为什么采用B+数作为索引？

MySQL索引的数据结构至少要满足：

  1. 尽可能少的磁盘IO操作中完成查询，磁盘IO是耗时很大的相比直接读内存
  2. 高效查询一条记录，高效的范围查询

MySQL单表数据不要超过2000w？

索引失效？

  1. 对索引使用左或者左右模糊匹配，%在左边的话就不知道从哪个索引值开始比较，只能全表扫描
  2. 对索引使用函数、表达式运算，索引保存的是原始值
  3. 对索引进行隐式类型转化，索引类型是字符串，输入的参数为整型
  4. 违反最左匹配原则，比如联合索引是abc，输入bc、c都是where中条件顺序不影响
  5. 范围查询的时候使用><，导致后续使用的索引失效
  6. where中or前使用索引，后不使用索引，全部失效。

执行一条更新语句的具体流程？

比如执行update user set name = "job" where id =1，结合redo log、undo log和binlog说一下流程

  1. 执行器负责具体执行，调用存储引擎的接口，通过主键索引查找id=1的这一条记录

    1. 如果该记录所在的数据页存在buffer pool中，那么直接返回给执行器

      如果不存在，那么将数据页从磁盘读取之后保存到buffer pool，然后将记录返回给执行器

  2. 执行器判断更新前后的值是否相同

    1. 相同，则直接返回不进行后续操作
    2. 不相同，更新前后的记录都交给InnoDB层，让其进行真正的更新操作

  3. 开启事务，InnoDB层在更新记录之前需要记录undo log日志，更新操作的话就是记录更新前的记录，生成的一条undo log需要放到buffer pool的undo页面，内存修改undo页也需要记录对应的redo log

  4. 开始执行更新操作，更新完成之后会将该记录所在的页标记为脏页，然后将该记录写入redo log中。为了减少磁盘IO，脏页是由后续的后台线程选择合适的时间写入磁盘（WAL技术）。MySQL写操作不是立刻写到磁盘，而是先写redo日志，然后在合适的时间写入磁盘中

  5. 此时update操作执行完毕了

  6. 更新语句执行完成之后需要记录binlog日志，先被保存到binlog cache，并没有刷新到磁盘上，等到事务提交再进行刷盘（默认）

  7. 事务提交：为了防止binlog和redo log不一致导致主从不一致的现象，分为了两个阶段进行提交（减少磁盘IO、增加并发性进行组提交） 使用XA分布式事务保持两者一致性，更新之后存储相应XID

    1. prepare阶段：将redo log对应的事务状态设置为 prepare，然后将 redo log 刷新到硬盘
    2. commit阶段：将binlog刷新到磁盘，接着调用引擎的提交事务接口，将redo log状态设置为commit(将事务设置为 commit 状态后，刷入到磁盘 redo log 文件)

  8. 更新语句全部成功
