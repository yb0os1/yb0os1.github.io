初始JVM

JVM：Java Virtual Machine，java虚拟机，本质上就是一个运行在计算机的程序，职责就是运行java字节码文件

功能

  1. 解释和运行：将java字节码文件的指令解释成机器码，让计算机执行

  2. 内存管理：自动为对象方法等分配内存、自动的垃圾回收（回收不在使用的对象）

  3. 即时编译：对热点代码进行优化，提升执行效率

    1. 由于JVM需要实时解释虚拟机指令，不做任何优化性能不如直接运行机器码的C、C++等语言（也就是每次都要将字节码解释成机器码）
    2. 即时编译可以性能优化，最终能达到接近C、C++语言的运行性能

常见虚拟机

JVM需要满足的规范：

  • 《Java虚拟机规范》由Oracle制定，内容主要包含了Java虚拟机在设计和实现时需要遵守的规范，主要包含class字节码文件的定义、类和接口的加载和初始化、指令集等内容。
  • 《Java虚拟机规范》是对虚拟机设计的要求，而不是对ava设计的要求，也就是说虚拟机可以运行在其他的语言比如Groovy、Scala生成的class字节码文件之上。

加载阶段 - 可验证静态变量存储空间

加载是第一步，作用：类加载器根据类的全限定名通过一些渠道获取字节码信息，保存到方法区还要和其关联的堆区中

1、类加载器根据类的全限定名通过不同的渠道以二进制流的方式获取字节码信息

不同渠道：本地文件、动态代理、通过网络传输的类

2、类加载器在加载完类之后，Java虚拟机会将字节码中的信息保存到方法区中

  • 方法区是一个虚概念
  • 生成InstanceKlass对象，保存类的所有信息，还包含实现特定功能（多态信息）

3、Java虚拟机还会在堆中生成一份和方法区中数据类似的java.lang.Class对象

  • 作用是：在Java代码中去获取类的信息以及存储静态字段的数据（JDK8之后）

  • 在JDK 7及以前的版本中，静态变量存储在方法区（也叫永久代）中。方法区存储类元数据，包括类结构信息（如字段、方法、字节码等），以及静态变量；从JDK 8开始，永久代被移除，方法区的功能由元空间（Metaspace）取代，但静态变量不再存储在元空间中

  • 从JDK 8开始，静态变量被存储在堆区。具体来说，类的静态变量随着类的加载被分配在Java堆中，而类的元数据存储在元空间（Metaspace）中

  • 反射的实现

  • 方法区存储的InstanceKlass会和堆区中存储的Class对象关联起来

连接阶段

校验和前期准备工作

分为三部分：

  • 验证：验证字节码是否满足Java虚拟机规范
  • 准备：给静态变量赋值
  • 解析：将常量池中的符号引用替换成指向内容的直接引用

验证

连接(Linking)阶段的第一个环节是验证，验证的主要目的是检测Java字节码文件是否遵守了《Java虚拟机规范》中的约束。这个阶段一般不需要程序员参与。

主要包含如下四个部分，具体在《Java虚拟机规范》

  1. 文件格式验证，Class文件以cafebabe开头；主次版本号

  1. 元信息验证，例如类必须有父类
  2. 验证程序执行指令的语义，例如方法内的指令执行中是否跳转到了不正确的位置
  3. 符号引用验证，例如是否访问了其他类中private的方法等

准备

准备阶段为静态变量(static)分配内存并设置初始值

（注意:本章涉及到的内存结构只讨论JDK8及之后的版本，8之前的版本后续章节详述）

双亲委派机制（核心知识点）

Java虚拟机有多个类加载器，双亲委派机制就是解决一个类到底由谁加载的问题

作用

  1. 保证类加载的安全性：通过双亲委派机制避免恶意代码替换JDK中的核心类库，比如java.lang.string，确保核心类库的完整性和安全性
  2. 避免类重复加载：双亲委派机制可以避免同一个类被多次加载

流程：当一个类加载器接收到加载类的任务时，会自底向上查找是否加载过（若加载过就结束），再由顶向下加载（这里是尝试加载，如果该类不在加载目录，那么就给子类加载）

**核心问题：**类的双亲委派机制是什么？

  1. （类加载的流程）当一个类加载器加载类时，首先会自底向上查看该类是否加载过，如果有类加载器加载过，那么直接返回；如果都没加载过，那么然后自顶向下进行加载，类加载器加载目录中有该类进行加载，否则向下传递
  2. （父子关系）应用程序加载类的父类是扩展类加载器，扩展类加载器的父类是启动类加载器
  3. （优点）首先：避免类的重复加载，其次：避免恶意代码替换JDK中的核心类库，如String，确保核心类库的完整性和安全性

Java虚拟机栈

概述

Java虚拟机栈（Java Virtual Machine stack）采用栈的数据结构来管理方法调用中的基本数据，先进后出（First In Last Out），每一个方法的调用使用一个栈帧（Stack Frame）来保存

执行方法，方法对应的栈帧入栈；方法执行完毕，对应栈帧出栈

可以通过idea的debug查看栈帧

并且当抛出异常的时候，java会把当前线程的栈内所有的栈帧依次弹出（并且打印对应报错代码的行数）

小总结：

  • Java虚拟机栈随着线程的创建而创建，而回收则会在线程的销毁时进行

  • 由于方法可能会在不同线程中执行，每个线程都会包含一个自己的虚拟机栈

栈帧组成
  1. 局部变量表：存放运行过程中的所有局部变量
  2. 操作数栈：栈帧中虚拟机在执行指令过程中用来存放临时数据的一块区域
  3. 帧数据：主要包含动态链接、方法出口、异常表和引用

堆内存

概述

线程共享区域

  • 创建出来的对象一般都位于堆上
  • 一般Java程序中堆内存是空间最大的一块内存区域
  • 栈上的局部变量表中，可以存放堆上对象的引用
  • 静态变量（JDK8之后存放在堆中）也可以存放堆对象的引用，通过静态变量就可以实现对象在线程之间共享

堆内存是会溢出的：

  • 堆内存大小是有上限的，当对象一直向堆中放入对象达到上限之后，就会抛出outofMemory
  • JVM默认分配的堆内存是很大的

详解

堆空间三个重要的值：used、total、max

used指的是当前已使用的堆内存，total是Java虚拟机已经分配的可用堆内存，max是Java虚拟机可以分配的最大堆内存

可以通过arthas的dashboard查看

手动指定刷新频率（不指定默认5秒一次）：dashboard-i 刷新频率(毫秒)

memory可以查看内存

堆内存溢出并不是当used=total=max的时候，判断条件复杂，和《垃圾回收器》有关

如果不设置任何的虚拟机参数，max默认是系统内存的1/4，total默认是系统内存的1/64
在实际应用中一般都需要设置total和max的值

手动设置：

  • -Xmx值修改max，-Xms修改total
  • 单位：字节（默认，1024倍数）、k或者K（KB）、m或者M（MB）、g
  • 限制max必须大于2MB，total必须大于1MB

我们可以发现，arthas显示的值和设置的值不一样，为什么？

arthas中的heap堆内存使用了JMX技术中内存获取方式，这种方式与垃圾回收器有关，计算的是可以分配对象的内存，而不是整个内存

就是说，虽然设置的total=2048MB，但是实际上可以分配对象的内存只有1963MB

总结

  • Java服务端程序开发时**，建议将-Xmx和-Xms设置为相同的值**，这样在程序启动之后可使用的总内存就是最大内存，而无需向java虚拟机再次申请，减少了申请并分配内存时间上的开销，同时也不会出现内存过剩之后堆收缩的情况
  • -Xmx具体设置的值与实际的应用程序运行环境有关，在《实战篇》中会给出设置方案

直接内存

直接内存(Direct Memory)并不在《Java虚拟机规范》中存在，所以并不属于Java运行时的内存区域

JDK1.4使用NIO机制，使用了直接内存，主要解决：

  1. Java堆中的对象如果不再使用就要回收，回收时会影响对象的创建和使用
  2. IO操作比如读文件，需要先把文件读入直接内存(缓冲区)再把数据复制到Java堆中

现在直接放入直接内存即可，同时Java堆上维护直接内存的引用，减少了数据复制的开销。写文件也是类似的思路

自动垃圾回收机制

概述

  • C/C++中一个不在使用的对象，需要手动释放，否则会出现内存泄漏
  • 内存泄漏指的是不再使用的对象在系统中未被回收，内存泄漏的积累可能会导致内存溢出

Java为了简化对象的释放，引入了自动的垃圾回收（GC）机制，对堆上的内存进行回收

线程不共享的部分，都是伴随着线程的创建而创建，线程的销毁而销毁。而方法的栈帧在执行完方法之后就会
自动弹出栈并释放掉对应的内存。（程序计数器、栈）

应用场景：

  1. 解决系统僵死问题：大厂的系统出现的许多系统僵死问题都与频繁的垃圾回收有关
  2. 性能优化：对垃圾回收器进行合理的设置可以有效地提升程序的执行性能
  3. 面试题：常见垃圾回收器、常见垃圾回收算法、四种引用、项目使用了哪一种？等等

  2. 加载该类的类加载器已经被回收

SoftReference提供了一套队列机制:
1、软引用创建时，通过构造器传入引用队列
2、在软引用中包含的所有对象被回收时，该软引用对象会被放入引用队列
3、通过代码遍历引用队列，将SoftReference的强引用删除

实际应用：缓存

软引用也可以使用继承自SoftReference类的方式来实现，StudentRef类就是一个软引用对象，通过构造器传入软引用包含的对象，以及引用队列。

弱引用

弱引用的整体机制和软引用基本一致，区别在于弱引用包含的对象在垃圾回收时，不管内存够不够都会直接被回收

JDK1.2之后提供了WeakReference类来实现弱引用，弱引用主要用在ThreadLocal

弱引用本身也需要借助引用队列来回收

虚引用和终结器引用

常规开发不会用到

虚引用：也叫幽灵引用/幻影引用，不能通过虚引用对象获取到包含的对象。虚引用唯一的用途是当对象被垃圾回收器回收时可以接收到对应的通知。Java中使用PhantomReference实现了虚引用。直接内存中为了及时知道直接内存对象不再使用，从而回收内存，使用了虚引用来实现

终结器引用：在对象需要被回收时，终结器引用会关联对象并放置在Finalizer类中的引用队列中，在稍后由一条由FinalizerThread线程从队列中获取对象，然后执行对象的finalize方法，在对象第二次被回收时，该对象才被真正的回收

该个过程中可以在finalize方法中再将自身对象使用强引用关联上，但是不建议这样做

垃圾回收核心

对于GC算法的评价：

  1. 吞吐量

    吞吐量指的是 CPU 用于执行用户代码的时间与 CPU 总执行时间的比值，即吞吐量=执行用户代码时间/
    (执行用户代码时间 +GC时间)。吞吐量数值越高，垃圾回收的效率就越高

  2. 最大暂停时间
    STW的最大值

  3. 堆使用效率
    不同垃圾回收算法，对堆内存的使用方式是不同的。
    比如标记清除算法，可以使用完整的堆内存。而复制算法会将堆内存一分为二，每次只能使用一半内存。从堆使用效率上来说，标记清除算法要优于复制算法。

上述三种评价标准:堆使用效率、吞吐量，以及最大暂停时间不可兼得。

一般来说，堆内存越大，最大暂停时间就越长。想要减少最大暂停时间，就会降低吞吐量

不同的垃圾回收算法，适用于不同的场景

GC算法-标记清除算法

核心思想：

  1. 标记阶段：将所有存活的对象进行标记（通过可达性分析算法，从GC Root通过引用链找到所有存活对象）
  2. 清楚阶段：从内存中删除没有被标记（非存活）对象

优点：

实现简单，只需要在第一阶段给每个对象维护标志位，第二阶段删除对象即可

缺点：

  1. 碎片化问题
    由于内存是连续的，所以在对象被删除之后，内存中会出现很多细小的可用内存单元。如果我们需要的是一个比较大的空间，很有可能这些内存单元的大小过小无法进行分配。

  2. 分配速度慢
    由于内存碎片的存在，需要维护一个空闲链表，极有可能发生每次需要遍历到链表的最后才能获得合适的内存空间

    遍历到链表尾部才可以找到

GC算法-复制算法

核心思想

  1. 准备两块空间from和to，每次在对象分配阶段只能使用其中一块空间（from空间）
  2. 在垃圾回收GC阶段，将from中存活的对象复制到to中
  3. 将两块空间名字调换（to空间存放的需要回收的对象，直接清理）

优点

  1. 解决了碎片化的问题
    复制算法在复制之后就会将对象按顺序放入To空间中，所以对象以外的区域都是可用空间，不存在碎片化内存空间
  2. 吞吐量高
    复制算法只需要遍历一次存活对象复制到To空间即可，比标记-整理算法少了一次遍历的过程，因而性能较好，但是不如标记-清除算法，因为标记清除算法不需要进行对象的移动

缺点

堆内存空间利用率低：每次只能让一半的内存空间来为创建对象使用

GC算法-标记整理算法

也将标记压缩算法，对标记清理算法容易产生内存碎片问题的一种解决方案

核心思想

  1. 标记阶段：将所有存活的对象进行标记（通过可达性分析算法，从GC Root通过引用链找到所有存活对象）
  2. 整理阶段：将存活的对象移动到堆的一端，清理掉没有标记的内存空间

优点

  1. 内存使用效率高
    整个堆内存都可以使用，不会像复制算法只能使用半个堆内存
  2. 不会发生碎片化
    在整理阶段可以将对象往内存的一侧进行移动，剩下的空间都是可以分配对象的有效空间

缺点

整理阶段效率不高

  • 整理算法有很多种，比如Lisp2整理算法需要对整个堆中的对象搜索3次，整体性能不佳。可以通过Two-Finger、表格算法、ImmixGc等高效的整理算法优化此阶段的性能

GC算法-分代算法（重要）

现代优秀的垃圾回收算法，将上述的垃圾回收算法组合进行使用，现在应用最广的垃圾回收算法

分代算法将堆内存分为：年轻代和老年代

  • （新生代）年轻代：存放存活时间比较短的对象
    • 伊甸园区（Eden）
    • 幸存者区S0
    • 幸存者区S1
  • 老年代：存放存活时间比较长的对象

有关堆、新生代、老年代的内存设置

-XX:UseSerialGC：设置为分代垃圾回收算法

分代GC的核心思想（步骤）：

  1. 刚创建的对象会放在年轻代的伊甸园区
  2. 随着创建的对象越来越多，若eden区满了，就会触发年轻代的GC，Young GC/Minor GC
  3. Minor GC会把Eden区和from区需要回收的对象进行回收，把存活的对象放到to区（S0和S1分别代表这from和to）
  4. 如果回收完之后，to区内存空间无法放全部的Eden区和from区的对象，那么将多出来的放到老年代
  5. 将S0和S1代表的含义进行交换
  6. 当Eden区再次满的时候，继续上述的Minor GC。每次Minor GC都会记录年轻代中对象的年龄，初始值为0，每次GC+1
  7. 如果Minor GC后对象的年龄达到阈值（JVM规定最大为15，具体的默认值和垃圾回收器有关），对象就晋升到老年代
  8. 当老年代中空间不足，无法放入新的对象时，先尝试minor gc如果还是不足，就会触发Full GC，full GC会对整个堆进行垃圾回收（Full GC的STW很长，minor GC的STW比较短）
  9. 如果Full GC依然无法回收掉老年代的对象（老年代内存空间依旧是满的），那么当对象继续放入老年代时，就会抛出Out Of Memory异常

什么时候对象会放到老年代？

  1. 新生代中对象的年龄达到阈值
  2. 新生代内存已经满了，该对象还想要放入新生代时

为什么划分了新生代和老年代？

一些关于此的前置：

  1. 系统中很多的对象都是创建之后很快就不在使用，可以被回收。比如用户获取订单数据、订单数据返回给用户之后就可以释放了
  2. 老年代中会存放长期存活的对象。比如Spring的大部分Bean对象，在程序启动之后就不会被回收
  3. 在虚拟机默认设置中，新生代的大小要远小于老生代的大小

对于问题的回答：

  1. 可以通过调整年轻代和老年代的比例来适应不同类型的应用程序，提高内存的利用率和性能
  2. 新生代和老生代使用不同的垃圾回收算法
    • 新生代一般使用复制算法
    • 老生代一般使用标记-清除算法或者标记-整理算法，由程序员决定灵活性高
  3. 分代的设计只允许回收新生代（minor gc），如果能满足对象分配的要求就不需要对整个堆进行回收（full gc），STW就会缩短 最核心的思想

老年代-CMS回收器

CMS：Concurrent Mark Sweep

CMS垃圾回收器关注的是系统的暂停时间，允许用户线程和垃圾回收线程在某些步骤中同时执行，减少了用户线程的等待时间

回收年代：老年代，算法：标记清除算法

优点：系统因垃圾回收出现的停顿时间较短，用户体验好

缺点：

  1. 内存碎片问题：标记清除算法存在，CMS会在full GC时进行碎片整理，会导致用户线程暂停，可以使用-XX:CMSFUllGCsBeforeCompaction=N默认0 调整N次Full GC后进行碎片整理
  2. 退化问题：如果老年代内存不足无法分配对象，CMS就会退化到SerialOld单线程回收老年代
  3. 浮动垃圾问题：并发清理过程中产生的浮动垃圾，不能做到完全的垃圾回收

使用场景：大型的互联网系统中用户请求数据量大、频率高的场景比如订单接口、商品接口等

执行步骤

  1. 初始标记：极短的时间内标记出GC Roots能直接关联的对象
  2. 并发标记：标记所有对象，用户线程不需要暂停
  3. 重新标记：由于并发标记阶段有些对象会发生了变化，存在错标、漏标等情况，需要重新标记
  4. 并发清理：清理死亡的对象，用户线程不需要暂停

G1垃圾回收器（JDK9之后默认）

Garbage First垃圾回收器

  • parallel scavenge关注吞吐量，允许用户设置最大暂停时间，但是减少年轻代可用空间的大小
  • CMS关注暂停时间，但是吞吐量方面会下降

G1设计目标就是结合上述两者垃圾回收器的优点融合：

  1. 支持巨大的堆空间回收，并有较高的吞吐量
  2. 支持多CPU并行垃圾回收
  3. 允许用户设置最大暂停时间

G1将整个堆划分多个大小相等的区域，称为Region，区域不要求连续

G1垃圾回收的方式：

  1. 年轻代回收（Young GC）
  2. 混合回收（Mixed GC）
流程

回收Eden区和Survivor区中非存活对象。会导致STW，G1中可以通过参数-XX:MaxGCPauseMillis=m（默认200ms）来设置每次垃圾回收的最大暂停时间毫秒数，G1垃圾回收器会尽可能保证暂停时间在设置范围之内

执行流程

  1. 新创建的对象会存放到Eden区，当G1判断年轻代内存不足（max默认为堆空间的60%）无法分配对象时，需要进行回收，执行Young GC

    Young GC流程

    • 标记出Eden和Survivor中存活的对象
    • 根据最大暂停时间选择某些要处理的区域（不是一次处理全部的区域），将存活对象复制到新的Survivor区中（年龄+1），清空被选择的区域
    • 怎么进行选择？
      • G1在进行Young GC的过程中会记录每次垃圾回收时每个Eden和Survivor的平均耗时，作为下次垃圾回收时的参考依据。这样就可以根据配置的最大暂停时间来计算出每次垃圾回收最多能处理多少个区域
      • 例如：使用默认的最大暂停时间（200m），每个region回收耗时为40m，那么这次回收最多能回收4个
      • 回收5个很可能超过最大暂停时间，不能这样精准的保证

  2. 后续的Young GC和上述相同，当某个存活对象的年龄达到阈值（默认15），将会放到老年代

  3. 特殊情况：部分对象的大小超过Region的一半，直接放到老年代，这类称为Humongous

    • 例如堆内存是4G，计算的Region=2M，只要一个对象的大小超过1M，就直接放到老年代（Humongous）
    • 如果一个对象为6M，那么会横跨3个区域

  4. 随着程序的运行，多次的回收，会出现很多老年代，当老年代内存占用率达到阈值（-XX:InitiatingHeapOccupancyPercent默认45%）会触发混合回收Mixed GC。回收所有的年轻代、老年代部分对象和大对象区。采用复制算法

    Mined GC流程：分为初始标记、并发标记、最终标记、并发清理

    • 初始标记：标记GC Roots引用的对象为存活，并行执行并停止用户线程
    • 并发标记：将第一步中标记的对象引用的对象进行标记为存活
    • 最终标记：标记一些因为引用改变而漏标的对象，不管新创建、不再关联的对象
    • 并发复制清理：将存活的对象复制到别的region，不会产生内存碎片 使用STAB算法

  5. G1对老年代的清理会选择存活度低的区域进行回收，而不是全部回收，这样保证了回收效率较高

  6. 如果清理过程中发现没有足够的空的Region存放转移的对象，则会进行Full GC。单线程（JDK9）/多线程（之后）执行标记-整理算法，导致用户线程的暂停

使用

JDK9之后默认使用

  • -XX:+UseG1GC打开G1的开关
  • -XX:MaxGCPauseMillis=毫秒值最大暂停时间

回收年代：年轻代和老年代

算法：复制算法

优点：

  1. 对比较大的堆空间，延迟可控
  2. 不会产生内存碎片

内存调优

内存泄漏和内存溢出

内存泄漏：Java中一个对象不再使用但是它还在GC Roots引用链上，无法被垃圾回收器回收 =-》内存泄漏

内存泄漏绝大部分都是由堆内存泄漏引起的

少量的内存泄漏可以容忍，但是如果发生持续的内存泄漏，不管有多大的内存迟早会被消耗完，最终导致的结果就是内存溢出。但是产生内存溢出并不是只有内存泄漏这一种原因

持续的内存泄漏=》内存溢出

内存泄漏的常见场景

  1. 大型的Java后端应用中，在处理用户的请求之后，没有及时将用户的数据删除。随着用户请求数量越来越多，内存泄漏的对象占满了堆内存最终导致内存溢出；这种内存溢出会直接导致用户请求无法处理，影响用户的正常使用。重启可以恢复应用使用，但是在执行一段时间之后依然会出现内存溢出
  2. 分布式任务调度系统如Elastic-job、Quartz等进行任务调度时，被调度的Java应用在调度任务结束中出现了内存泄漏，最终导致多次调度之后内存溢出。这种产生的内存溢出会导致应用执行下次的调度任务执行。同样重启可以恢复应用使用，但是在调度执行一段时间之后依然会出现内存溢出

发现问题 – 堆内存状况

正常情况：

  • 处理业务时会出现上下起伏业务对象频繁创建内存会升高触发Minor Gc之后内存会降下来
  • 手动执行FULL GC之后，内存大小会骤降，而且每次降完之后的大小是接近的
  • 长时间观察内存曲线应该是在一个范围内

出现内存泄漏：

  • 处于持续增长的情况，即使Minor Gc也不能把大部分对象回收
  • 手动FULL GC之后的内存量每一次都在增长，长时间观察内存曲线持续增长

产生内存泄漏原因一：代码中的内存泄漏 工作不常见

1、equals和hashCode

上述代码很容易出现oom，对象作为key并且没有重写equal和hashCode，hashMap每次都认为是加入新对象

如果要class对象作为key，必须重写

并外一种使用Integer或者Long作为key 一定范围内有自动装箱，还是建议重写equal和hashCode

2、内部类引用外部类

非静态的内部类默认会持有外部类，尽管代码上不再使用外部类，所以如果有地方引用了这个非静态内部类，会导致外部类也被引用，垃圾回收时无法回收这个外部类（静态内部类不会持有外部类）

匿名内部类对象如果在非静态方法中被创建，会持有调用者对象，垃圾回收时无法回收调用者

3、ThreadLocal的使用

如果仅仅使用手动创建的线程，就算没有调用ThreadLocal的remove方法清理数据，也不会产生内存泄漏。因为当线程被回收时，ThreadLocal也同样被回收。但是如果使用线程池就不一定了

解决：线程方法执行完，一定要调用ThreadLocal中的remove方法清理对象

4、String的intern方法

把字符串放到常量池

JDK6中常量池在永久代，JDK8中常量池在堆区

5、静态字段保存对象 频率高

如果大量的数据在静态变量中被长期引用，数据就不会被释放，如果这些数据不再使用，就成为了内存泄漏

解决：

  1. 尽量减少将对象长时间的保存在静态变量中，如果不再使用，必须将对象删除(比如在集命中)或者将静态变量设置为null
  2. 使用单例模式时，尽量使用懒加载，而不是立即加载,
  3. Spring的Bean中不要长期存放大对象，如果是缓存用于提升性能，尽量设置过期时间定期失效.

6、资源没有正常关闭

连接和流这些资源会占用内存，如果使用完之后没有关闭，这部分内存不一定会出现内存泄漏，但是会导致close方法不被执行

解决：

  1. 为了防止出现这类的资源对象泄漏问题，必须在finally块中关闭不再使用的资源。
  2. 从 Java 7 开始，使用try-with-resources语法可以用于自动关闭资源。

产生内存泄漏原因二：并发请求问题 工作常见

并发请求问题指的是用户通过发送请求向Java应用获取数据

正常情况下Java应用将数据返回之后，这部分数据就可以释放

但是由于用户的并发请求量有可能很大，同时处理数据的时间很长，导致大量的数据存在于内存中，最终超过了内存的上限，导致内存溢出

这类问题的处理思路和内存泄漏类似，首先要定位到对象产生的根源

内存快照

当堆内存溢出时，需要在堆内存溢出时将整个堆内存保存下来，生成内存快照(Heap Profile )文件

  • 生成内存快照的Java虚拟机参数：

    • -XX:HeapDumpPath=<path>：指定hprof的输出目录

使用MAT打开hprof文件，并选择内存泄漏检测功能，MAT会自行根据内存快照中保存的数据分析内存泄漏的根源。

MAT内存泄漏检测的原理 – 支配树

MAT提供了称为支配树(Dominator Tree)的对象图。支配树展示的是对象实例间的支配关系。在对象引用图中，所有指向对象B的路径都经过对象A，则认为对象A支配对象B

分为深堆和浅堆

支配树中对象本身占用的空间称之为浅堆(Shallow Heap)

支配树中对象的子树就是所有被该对象支配的内容，这些内容组成了对象的深堆(Retained Heap)也称之为保留集(Retained Set)。深堆的大小表示该对象如果可以被回收，能释放多大的内存空间

MAT根据支配树，从叶子节点向根节点遍历，如果发现深堆的大小超过整个堆内存的一定比例阈值，就将其标记为内存泄漏的嫌疑对象
