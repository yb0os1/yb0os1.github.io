面试问答 - CPC广告排序系统

基于实际代码和文档整理的面试问答，涵盖项目背景、技术实现、性能优化等各个方面。

一、项目背景和业务理解

Q1: 请介绍一下这个项目的背景和业务需求？

回答：
这个项目是CPC广告智能排序系统，业务背景是：在携程旅游频道搜索列表页，当CPT广告不存在时，需要展示CPC广告（按点击付费的广告）。

核心需求：

  1. 展示场景：旅游频道搜索列表页（tabid=64和512）
  2. 广告位置：1+5N(N≤6)，即1、6、11、16、21、26、31位
  3. 排序目标：对50个CPC广告候选进行智能排序，平衡用户体验和广告收入
  4. 性能要求：单次请求（200个产品内）返回时间不超过80ms

业务价值：

  • 提升广告收入：在CPT广告缺失时，通过CPC广告填补广告位
  • 提升供应商ROI：通过智能排序，提高广告点击率和转化率

Q2: 广告排序的核心公式是什么？为什么这样设计？

回答：
核心排序公式是：rank_score = ctr × (cvr^α) × bid

公式组成：

  • ctr：点击率（Click-Through Rate），通过模型预测
  • cvr：转化率（Conversion Rate），通过模型预测
  • α：可调参数（通常为0.5-1.0），控制CVR的权重
  • bid：出价（Bid），从营销侧传入

设计原因：

  1. 多目标优化：CTR为主、CVR为辅，既考虑用户点击意愿，也考虑转化效果
  2. 平衡收入：引入出价bid，平衡用户体验和广告收入
  3. 可调参数：α参数可调，便于根据业务效果调整策略

实际实现：

  • 模型层面：黑盒模型可能已经融合了该公式，直接返回label_score
  • 代码层面：FusionScoringCalculator节点对特定场景（详情页来源）进行分数调整

Q3: "无CPT广告时展示CPC广告"这个判断逻辑在哪里实现？

回答：
这个判断逻辑不在广告排序服务中，而是在营销侧服务中实现的。

完整链路：

为什么不在广告排序服务中判断？

  1. 职责分离：广告排序服务专注于排序算法，不涉及业务决策
  2. 调用时机：营销侧在调用之前就已经判断过了
  3. 性能考虑：避免在排序服务中额外查询CPT广告数据
  4. 架构设计：营销侧作为业务层，负责业务逻辑判断；排序服务作为算法层，负责算法计算

二、技术架构和设计

Q4: 请介绍一下系统的技术架构？

回答：
系统采用分层架构，基于工作流编排模式：

分层架构：

  1. SOA层：对外提供RPC接口（RankPlatformServiceImpl）
  2. 路由层：根据bizId路由到对应服务（RankServiceRouter）
  3. 业务层：业务逻辑入口（PkgAdAdRankService）
  4. 处理器层：上下文处理、特征处理（AdContextProcessor、AdRankContextProcessor）
  5. 节点层：DAG节点，执行具体业务逻辑（16个节点）
  6. 操作层：封装具体操作（Ops层，因子和维度计算）

工作流编排：

  • 使用基于DAG的ChainWorkFlow引擎
  • 支持16步排序流程
  • 支持条件分支（addConditionalStep、addBranch）
  • 支持并行执行（ParallelFeatureAndFactorsAndIngest）

技术栈：

  • Java 21、Spring Boot
  • 工作流引擎（ChainWorkFlow）
  • 机器学习模型（黑盒模型预测CTR/CVR）
  • Redis（缓存特征数据）
  • CompletableFuture（异步并发）

Q5: 为什么使用工作流编排？有什么优势？

回答：
使用工作流编排（ChainWorkFlow）有以下优势：

1. 可维护性

  • 代码结构清晰，每个节点职责单一
  • 便于理解和调试，可以清楚地看到整个流程

2. 可配置性

  • 支持多版本算法配置，便于A/B测试
  • 可以通过配置切换不同的排序策略

3. 可扩展性

  • 新增功能只需添加新节点，不影响现有流程
  • 支持条件分支，可以根据不同场景走不同路径

4. 可观测性

  • 每个节点都有独立的监控和日志
  • 可以清楚地看到每个节点的执行时间和状态

Q6: 白盒排序和黑盒排序的区别？如何选择？

回答：
白盒排序：

  • 基于规则的排序
  • 使用预定义的规则和权重计算分数
  • 调用CoreRankProcessV2.getInstance().coreProcess()
  • 基于因子值和权重进行线性加权计算

黑盒排序：

  • 基于机器学习模型的排序
  • 调用外部模型服务预测CTR和CVR
  • 模型返回综合分数（可能已融合排序公式）
  • 更智能，但需要模型服务支持

选择逻辑：

  • 通过GetVersionInfo节点获取版本配置
  • 检查版本配置中是否有黑盒模型
  • 如果有黑盒模型 → 执行黑盒排序
  • 如果没有黑盒模型 → 执行白盒排序

三、核心实现细节

Q7: 黑盒排序是如何实现批量处理和异步并发的？

回答：
黑盒排序通过以下方式实现批量处理和异步并发：

1. 批量处理

  • 默认50个广告一批（可通过配置调整）
  • 使用Lists.partition将广告列表分批
  • 减少网络调用次数，提高性能

2. 异步并发

  • 使用CompletableFuture为每个批次创建异步任务
  • 多个批次并行调用模型服务
  • 使用CoreProcessThread.getExecutor()线程池执行
  • 最后通过collectResults合并所有批次的结果

3. 超时控制

  • 默认300ms超时（可通过配置调整）
  • 避免单个批次阻塞整个流程

4. 异常处理

  • 每个批次独立处理异常
  • 单个批次失败不影响其他批次
  • 记录日志便于排查问题

Q8: 特征工程是如何实现的？包含哪些特征？

回答：
特征工程通过多个节点实现，包括：

1. 组装特征维度（Step 3）

  • 用户特征：用户ID、用户星级、年龄、性别、常驻地等
  • 场景特征：搜索关键词、POI信息、出发城市、渠道等
  • 广告特征：广告位次、广告来源等

2. 计算维度并补充（Step 4）

  • 使用OpsExecutor并行计算因子、上下文维度、商品维度
  • 合并结果到上下文中

3. 并行执行特征和因子（Step 5）

  • 特征平台分数：从特征平台获取预计算分数
  • CTR因子：从Redis获取历史CTR数据，根据用户特征、商品特征匹配CTR
  • 黑名单用户本地因子：判断用户是否在黑名单中，计算用户本地因子
  • 三个任务并行执行，最后合并结果

4. 数据摄入（Step 6）

  • 整合之前计算的所有因子数据
  • 分类为白盒因子值（Double类型）和黑盒因子值（各种类型）

特征维度总结：

  • 用户维度：30+维度（用户ID、星级、年龄、性别、常驻地等）
  • 商品维度：商品ID、类型、天数、目的地等
  • 场景维度：搜索关键词、POI、出发城市、tabid等
  • 广告维度：出价、广告位次、广告来源等

使用场景：

优势：

  1. 轻量级：虚拟线程比平台线程更轻量，可以创建大量线程
  2. 高并发：适合IO密集型任务，如网络调用、数据库查询

实际效果：

  • 支持高并发请求处理
  • 提高系统吞吐量
  • 降低资源消耗

五、异常处理和容错

Q13: 系统如何处理异常？有哪些容错机制？

回答：
系统通过多层异常处理机制保证系统稳定性：

1. 节点级异常处理

  • 每个节点都有try-catch异常处理
  • 记录异常到监控系统（Cat）
  • 记录处理时间

2. 批次级异常处理

  • 单个批次失败不影响其他批次
  • 返回空结果，继续处理其他批次
  • 记录警告日志

3. 工作流级异常处理

  • 工作流引擎统一处理异常
  • 调用handleException方法

4. 全局异常处理

  • 记录异常日志和监控指标
  • 重置为默认商品，保证系统可用性
  • 不会因为异常导致系统崩溃

容错策略：

  1. 降级策略：异常时返回默认产品列表
  2. 部分失败容忍：单个批次失败不影响整体
  3. 监控告警：记录异常指标，便于及时发现问题
  4. 日志记录：详细记录异常信息，便于排查问题

Q15: 工作流的16步流程是如何设计的？为什么是16步？

回答：
16步流程设计遵循单一职责原则，每个步骤职责明确：

流程设计：

为什么是16步？

  1. 职责分离：每个步骤职责单一，便于维护和调试
  2. 可扩展性：新增功能只需添加新步骤，不影响现有流程

设计原则：

  • 单一职责：每个节点只做一件事
  • 开闭原则：对扩展开放，对修改关闭
  • 依赖倒置：依赖抽象，不依赖具体实现

难点4：异步并发和异常处理

解决方案：

常见追问

  1. 如果模型服务挂了怎么办？

    • 回答：有超时控制和异常处理，会返回默认产品列表，保证系统可用性

  2. 如何保证排序的公平性？

    • 回答：通过排序公式平衡CTR、CVR和出价，既考虑用户体验，也考虑广告收入

    • 回答：通过批量处理，将广告分批处理，最后合并结果

    • 回答：通过版本配置，支持多版本算法配置，可以根据不同用户走不同版本
